# Implement Complete Cart APIs

## Goal

Implement the complete **Cart domain** for the existing e-commerce backend.

The backend already has Authentication, Category APIs, and Product APIs implemented.

Now implement the Cart system as a clean, production-quality, scalable module that supports:

* Guest carts
* Logged-in customer carts
* Persistent customer carts
* Guest → customer cart merge
* Product + variant selection
* Multiple variant attributes
* Product modifiers
* Cart item configuration
* Cart metafields
* Cart item metafields
* Quantity management
* Price snapshots
* Stock/availability validation
* Cart totals
* Secure cart ownership
* Optimized PostgreSQL/Prisma queries
* Transaction-safe updates

The implementation must be generic enough to support different types of e-commerce businesses such as fashion, electronics, grocery, food, furniture, beauty, B2B, etc.

# 4. GUEST CART

Guests must be able to:

```text
Browse
↓
Product
↓
Select variant/modifiers if required
↓
Add to Cart
↓
View Cart
↓
Update Cart
↓
Remove Cart Items
↓
Proceed to Checkout
↓
Login/Register required
```

Login must NOT be required to create or use a cart.

A guest cart must use a secure cart identifier/token.

Do not expose sensitive internal database identifiers unnecessarily if the existing architecture supports a safer public identifier.

Guest cart ownership must be validated securely.

A guest must never be able to access another guest's cart.

---

# 5. CUSTOMER CART

Authenticated customers must have a persistent cart.

A customer should be able to:

* create/get their cart
* add products
* update quantities
* remove products
* clear cart
* view cart
* add/update/remove cart metafields
* add/update/remove cart item metafields

The customer's cart must persist in the database.

A customer must not be able to access another customer's cart.

Use authenticated customer identity from the existing authentication system.

Do not trust customer IDs supplied by the frontend when authentication already provides the identity.

---

# 6. ONE ACTIVE CART PER CUSTOMER

The database design should prevent unnecessary duplicate active carts for the same customer.

If the existing database design supports it, enforce this with a database-level constraint/index rather than relying only on application logic.

Guest carts can have their own lifecycle.

Keep the design flexible enough for future cart states such as:

```text
ACTIVE
CONVERTED
ABANDONED
EXPIRED
```

Do not over-engineer these states if the existing architecture does not require them yet.

# 7. GUEST → CUSTOMER CART MERGE

This is mandatory.

Example:

Guest cart:

```text
T-Shirt × 2
Shoes × 1
```

Customer already has:

```text
T-Shirt × 1
Jeans × 1
```

After login/merge:

```text
T-Shirt × 3
Shoes × 1
Jeans × 1
```

However, products must only be merged when the cart items represent the same purchasable configuration.

For example:

```text
T-Shirt
Black / Large
```

and

```text
T-Shirt
Black / Medium
```

must remain separate cart items.

The uniqueness/merge comparison must consider:

* product
* variant
* selected modifiers
* relevant configuration/options

Do not simply compare productId.

If the existing architecture has a login/register flow that can naturally trigger cart merging, integrate with it without breaking authentication.

Otherwise expose a dedicated merge operation that can be called after authentication.

# 8. PRODUCT + VARIANT SUPPORT

The existing Product system supports variants with multiple attributes.

Examples:

```text
Color = Black
Size = Large
```

or:

```text
Storage = 256GB
Color = Blue
```

Cart items must reference the exact selected variant where a variant exists.

Do not store only:

```text
productId
quantity
```

when a product requires a specific variant.

The cart must preserve the customer's exact configuration.

Use the existing Product/Variant structure rather than creating duplicate variant tables.

---

# 9. PRODUCTS WITHOUT VARIANTS

Products that do not require variant selection should be addable directly.

The existing Product API already exposes concepts such as:

```text
hasVariants
hasModifiers
requiresConfiguration
```

Use the existing product configuration rules.

Do not duplicate these rules inside the Cart unnecessarily.

The cart must still validate that the selected configuration is valid.

---

# 10. MODIFIERS

Modifiers are separate from variants.

Examples:

```text
Extra Cheese +₹40
Gift Wrapping +₹50
Engraving +₹100
```

A cart item must preserve the selected modifiers.

Validate that:

1. The modifier exists.
2. The modifier belongs to the relevant product/variant/configuration.
3. The selected modifier is currently active/purchasable.
4. The requested quantity/configuration is valid.
5. Modifier pricing is calculated safely.

Do not trust modifier prices sent by the frontend.

Always obtain authoritative pricing from the database.

---

# 11. CART ITEM CONFIGURATION

A cart item should be capable of representing:

```text
Product
Variant
Quantity
Selected modifiers
Selected options/configuration
Price information
```

Use normalized relational data where the information needs to be queried, validated, indexed, or related to existing entities.

Do not put the entire cart item into one giant JSON column.

JSON/JSONB should only be used where it provides a real benefit for flexible configuration data and does not replace relational data that needs to be queried.

---

# 12. CART ITEM UNIQUENESS

The same product can appear as multiple cart items when the configuration differs.

Example:

```text
T-Shirt
Black / Large
Quantity: 2

T-Shirt
Black / Medium
Quantity: 1
```

These must be separate cart items.

But:

```text
T-Shirt
Black / Large
Quantity: 2
```

added again with the exact same configuration should increase the existing quantity rather than unnecessarily creating another row.

The implementation must handle this safely under concurrent requests.

Do not rely only on a frontend check.

Use proper database constraints/transactions where appropriate.

---

# 13. PRICE SNAPSHOT

Cart items must preserve the relevant pricing information at the time they are added/updated.

The existing product pricing model supports:

```text
Regular Price
Sale Price
Offer Price
Effective Price
Discount Percentage
```

Coupons and promotions are separate systems and must NOT be mixed into product pricing.

The cart should be designed around:

```text
Product pricing
↓
Cart item pricing
↓
Future Promotion Engine
↓
Future Coupon Engine
↓
Checkout
```

Do not implement the Promotion/Coupon engine now.

Do not hardcode discount logic inside Cart.

Money must use the existing Prisma/PostgreSQL Decimal-safe approach.

Never use JavaScript floating-point arithmetic for monetary calculations.

Do not trust frontend-supplied prices.

The server must always determine authoritative pricing.

---

# 14. PRICE REVALIDATION

Product prices can change after a customer adds an item to their cart.

Therefore, when reading/updating the cart and especially before checkout, the system must have a clear mechanism for determining whether cart pricing is still valid.

For this Cart implementation:

* preserve the cart item's relevant price snapshot
* compare/revalidate against current product/variant/modifier pricing when appropriate
* expose a clear price/availability state to the frontend
* never allow the frontend to determine the final authoritative price

Do not silently charge an outdated price.

Do not implement final checkout/order pricing yet.

---

# 15. INVENTORY / STOCK

Inventory belongs to the Product/Admin/Inventory domain, NOT the Cart domain.

Cart must NOT become the source of truth for inventory.

The Cart should only validate current availability.

Examples:

### Product in stock

```text
Requested quantity: 2
Available stock: 10

→ Allow
```

### Partial stock

```text
Requested quantity: 5
Available stock: 2

→ Reject/update request
→ Return available quantity: 2
```

### Out of stock

```text
Requested quantity: 1
Available stock: 0

→ Do not allow adding/updating
→ Cart item should expose an OUT_OF_STOCK state
```

If a product becomes out of stock after already being added to the cart:

**Do NOT silently remove the cart item.**

Return a clear availability state so the frontend can tell the customer:

```text
This product is currently out of stock.
```

or:

```text
Only 2 items are currently available.
```

The cart should support states such as:

```text
AVAILABLE
OUT_OF_STOCK
INSUFFICIENT_STOCK
```

Use the project's existing product/inventory fields.

If inventory is not yet implemented in the existing Product domain, do NOT create an unnecessarily large inventory system as part of this task.

Instead, create clean validation hooks/interfaces/functions so inventory can be integrated later.

Important:

**Do not reserve/decrement stock merely because an item was added to cart.**

Actual stock reservation/decrement should happen later during checkout/order creation using a database transaction.

# 16. CART METAFIELDS

Implement flexible Cart Metafields.

Do NOT add arbitrary hardcoded columns such as:

```text
giftMessage
campaignId
externalReference
marketingSource
```

directly to the Cart table.

Use a generic metafield structure.

Conceptually:

```text
Cart
  ↓
CartMetafield
```

A metafield should support information such as:

```text
namespace
key
value
valueType
```

Example:

```json
{
  "namespace": "checkout",
  "key": "gift_message",
  "value": "Happy Birthday!",
  "valueType": "STRING"
}
```

Another example:

```json
{
  "namespace": "marketing",
  "key": "campaign_id",
  "value": "DIWALI2026",
  "valueType": "STRING"
}
```

The schema should be reusable for future Order Metafields.

Do not create a separate completely different metafield architecture for Orders later.

# 21. CART MERGE API

Provide a safe operation for guest → customer cart merge.

Conceptually:

```text
POST /carts/merge
```

Input may contain the guest cart identifier/token.

The authenticated user must be taken from the authentication context.

Do not allow the client to specify another customer's ID.

Merge rules must:

* preserve valid guest items
* combine identical configurations
* keep different configurations separate
* validate current product/variant/modifier availability
* validate stock
* handle quantity conflicts safely
* preserve appropriate cart metafields according to a clearly defined rule
* avoid duplicate active carts
* execute safely in a transaction

After successful merge, the guest cart should no longer remain as an active independent cart.
