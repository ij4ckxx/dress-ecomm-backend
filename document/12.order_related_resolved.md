# Confirmed Requirements: Order Management and Admin Workflow

The overall assessment is approved, with the following clarifications and requirements. Before implementation, inspect the existing codebase and preserve all existing functionality. Do not break or unnecessarily modify the existing checkout, cart, authentication, product, inventory, or admin functionality.

## 1. Order Identifier

Use the human-readable `orderNumber` in customer-facing URLs and API routes wherever practical.

Example:

* `GET /api/v1/orders/:orderNumber/confirmation`
* `GET /api/v1/orders/:orderNumber`
* `POST /api/v1/orders/:orderNumber/cancel`
* `POST /api/v1/orders/:orderNumber/reorder`

The backend must resolve the order securely and verify ownership against the authenticated customer. Internal UUIDs may continue to be used for database relations and internal admin operations.

## 2. Order Status and Admin Control

The admin must have the ability to view orders and manage their status through the admin panel. Customers must see the latest status in Order History, Order Confirmation, and Order Details.

Review the existing order status enum and transition logic before making changes. Reuse existing status values wherever possible.

The admin should be able to perform appropriate transitions, such as:

* `PENDING`: Order placed and awaiting review or confirmation.
* `CONFIRMED`: Order accepted by the store.
* `PROCESSING`: Order preparation has started.
* `SHIPPED`: Order dispatched to the courier.
* `DELIVERED`: Order delivered to the customer.
* `CANCELLED`: Order cancelled.
* `REFUNDED` or partial refund states, if supported by the payment system.

Do not blindly add duplicate or incompatible status values. Adapt this list to the existing schema and business logic.

Admin status updates must be validated on the backend. Record status changes in the existing status history system, including timestamps and the responsible admin where appropriate. Customers must never be allowed to change their own order status.

Keep payment status separate from fulfilment/order status.

## 3. Cash on Delivery (COD) Workflow

COD is an important payment method and must be handled separately from online payment verification.

When a customer places a COD order:

1. Validate the cart, prices, inventory, shipping address, and order details on the backend.
2. Create the order with the appropriate initial order status, normally `PENDING`, following the existing implementation.
3. Set the payment method to COD and payment status to an appropriate unpaid or pending state.
4. Save the order and its items consistently.
5. Redirect the customer to the Order Confirmation page after successful order creation.
6. Send an order notification email to the configured admin/store email address.
7. Allow the admin to open the order in the admin panel, review the details, and confirm, process, ship, deliver, or cancel it according to the allowed status transitions.
8. Update the customer-facing order pages whenever the order status changes.

The admin email should contain the order number, order date, customer contact details required for fulfilment, shipping address, product names, variants, quantities, order total, payment method, and a secure link to the admin order details page.

Do not include passwords, authentication tokens, or other sensitive credentials in emails. The admin link must require normal admin authentication and authorization.

Use the existing email service and notification patterns if available. If email delivery fails, do not silently lose the order or create a duplicate order. Log the failure and use the project's existing retry or notification mechanism where available.

For COD, do not mark the order as paid when it is placed. Payment should be marked as collected only when the applicable collection event is verified or recorded by an authorized admin. Delivery and payment collection must not be treated as automatically identical events.

If the project already supports online payments, preserve that flow and its payment verification rules.

## 4. Customer Order Cancellation

Allow customers to request cancellation only while the order is in `PENDING`, as long as the existing workflow can safely support this rule.

The cancellation endpoint must verify ownership, validate the current status, and prevent conflicting simultaneous updates.

Inventory must be restored exactly once when cancellation is finalized, using a database transaction and the existing inventory logic. Avoid double-restocking if the cancellation endpoint is retried.

If the current inventory or order workflow requires a different cancellation process, inspect it first and implement the safest compatible solution.

## 5. Reorder Behavior

The Reorder action must merge eligible products into the customer's existing active cart rather than replace the current cart.

Before adding each item, validate that the product and selected variant still exist, are available for purchase, and have sufficient stock. Use the current product prices rather than blindly reusing historical prices.

If an item or variant is unavailable, do not fail the entire operation unnecessarily. Add eligible items and return clear information about skipped or quantity-adjusted items. Follow the existing cart merge and stock validation rules.

## 6. Order Metafields

Create an `OrderMetafield` model using the existing Prisma conventions and the proposed namespace, key, value, value type, description, visibility, and timestamps.

Use a unique constraint on `[orderId, namespace, key]` and appropriate indexes, after confirming compatibility with the current schema.

Support both customer-visible metadata and private operational metadata. Customer APIs must return only explicitly permitted public metafields. Admin APIs may access private metadata subject to authorization.

During checkout, copy appropriate cart metafields into the order as part of the order creation transaction. Validate the allowed namespaces and keys, and do not allow cart metadata to override authoritative prices, payment status, order status, or security-related fields.

Provide admin APIs to list, create or update, and delete order metafields. Reuse existing validation and service patterns.

## 7. Order Confirmation, History, and Details

Implement or enhance the following:

* Order Confirmation: order number, products, variant details, quantity, pricing breakdown, shipping/billing addresses, payment method, payment status, order status, and available delivery/tracking information.
* Order History: a compact, paginated list of the authenticated customer's orders, including order number, date, product preview, item count, total, order status, payment status, and a View Details action.
* Order Details: complete historical product snapshots, pricing, addresses, status history, courier partner, tracking number, estimated delivery where available, and permitted customer-visible metafields.

Only display courier, tracking, and estimated delivery details when actual data is available. Do not invent tracking details or delivery dates.

## 8. Admin Order Management

Enhance the existing admin order details API and UI without duplicating existing functionality.

The admin must be able to:

* View complete order information and all authorized metafields.
* Review customer and shipping details.
* View the payment method and payment status.
* Change the order status through validated actions.
* Record payment collection for COD when appropriate.
* Add or update courier partner, tracking number, and estimated delivery information when those fields are supported by the existing schema.
* Manage order metafields, including private operational metadata.
* View the order status history and relevant timestamps.

The admin UI must clearly distinguish order status from payment status. Do not introduce fake payment, tracking, refund, or delivery functionality.

## 9. Database Changes and Safe Implementation

Before changing the database, inspect the existing Prisma schema, migration history, database environment, and project scripts.

Prefer the project's established Prisma migration workflow for a schema change. Do not run `npx prisma db push` against a shared or production database without explicit approval and a verified backup/change plan. Do not assume that a schema change cannot affect existing data without checking the generated changes.

First report the files, models, APIs, and admin components that need modification. Then implement the work in small steps, validate the schema, run appropriate migrations in the intended development environment, and execute relevant tests.

Do not break existing functionality. At the end, report all changed files, database changes, APIs implemented, tests performed, and any remaining limitations.

Proceed with this clarified plan after inspecting the existing codebase.

## Final Decisions and Implementation Requirements

Implement the order management functionality according to the following confirmed decisions:

1. **Customer Order URLs:** Use the human-readable `orderNumber` in customer-facing URLs and API routes.

2. **Customer Cancellation:** Allow customers to cancel their orders only while the order status is `PENDING`. Validate ownership and status on the backend, and restore inventory exactly once when cancellation is finalized.

3. **Reorder:** Merge eligible products from a previous order into the customer's existing active cart. Validate current product availability, variants, stock, and prices before adding items.

4. **COD Order Creation:** When a Cash on Delivery (COD) order is successfully placed, create the order with the appropriate initial status and keep its payment status unpaid or pending. Do not mark it as paid automatically.

5. **COD Admin Notification:** Send an email notification to the configured admin/store email address after a COD order is successfully created. Include the order number, customer and shipping details, purchased products, quantities, order total, and payment method. Handle email failures using the existing notification or retry mechanism wherever available.

6. **Admin Status Control:** Provide the admin with the ability to view orders and manage their status through the admin panel. Validate status transitions on the backend and maintain order status history. Customers must only be able to view their order status, not modify it.

7. **COD Payment Collection:** Allow an authorized admin to record COD payment collection when it has actually been received or verified. Keep payment status separate from order fulfilment status.

8. **Order Metafields:** Implement order metafields with support for public customer-visible metadata and private internal operational metadata. Enforce backend authorization and filter private metafields from customer-facing APIs. Copy appropriate cart metafields to the order during checkout, where applicable.

9. **Database Migration:** Inspect the existing Prisma schema, migration history, database environment, and project conventions before making changes. Use the established migration workflow safely. Do not run schema-changing commands against shared or production databases without explicit approval and an appropriate backup/change plan.

### Important Business Rule

Order confirmation means that the order has been successfully placed; it does not necessarily mean that payment has been received or that the order has been accepted, shipped, or delivered.

For COD orders, the admin should be able to review and confirm the order, initiate processing, update shipping and delivery information, manage status transitions, and record payment collection according to the actual workflow.

### Implementation Instructions

Before coding, inspect the existing codebase and identify the files, APIs, database models, and admin components that require changes. Reuse existing functionality wherever possible, avoid unnecessary architectural changes, and do not break the existing checkout, cart, authentication, product, inventory, or admin functionality.

Implement the changes incrementally, validate the complete customer and admin order workflows, run the relevant tests, and report the files changed, database changes, APIs implemented, tests performed, and any remaining limitations.
