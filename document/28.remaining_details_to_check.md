2. Modifiers (Partially Working ⚠️ – Key Gaps Identified)
In BigCommerce Catalyst, modifiers allow customers to customize a product without creating dozens of separate SKUs. Catalyst supports multiple distinct UI control types:

Dropdown (e.g., Select Neckline: V-neck, Boat-neck, Halter)
Radio Buttons / Rectangles / Swatches (e.g., Select Fabric: Pure Silk, Chiffon, Georgette)
Checkbox (e.g., "Add Matching Dupatta/Scarf (+₹499)", "Add Luxury Gift Box (+₹150)")
Short Text Field (e.g., "Custom Monogram / Name Embroidery" – up to 15 characters)
Multi-line Text / Textarea (e.g., "Gift Card Message" or "Custom Blouse Measurement Notes")
Numbers Only (e.g., Custom dress length in cm)
Date Picker (e.g., Event/Wedding date for tailored delivery)
File Upload (e.g., Custom embroidery reference photo)
What our backend currently does:
Price Delta: Working ✅. If a modifier option has a priceDelta (e.g., +₹150), cart.service.js and checkout.service.js add it to the unit price (effectiveUnitPrice = unitPrice + modifierTotal).
Selection limits: minSelection and maxSelection are enforced during cart validation.
What is MISSING compared to BigCommerce Catalyst:
No type field on ModifierGroup:
In our database schema (prisma/schema/catalog.prisma), ModifierGroup only has name, isRequired, minSelection, and maxSelection. It has no type enum (like DROPDOWN, SWATCH, CHECKBOX, TEXT, TEXTAREA).
Problem: The frontend doesn't know whether to display it as a dropdown, a radio button, a checkbox, or a text box.
Free-form Text Modifiers are impossible right now:
If a customer wants custom embroidery text (e.g. typing their name "Ananya"), our CartItemModifier only accepts modifierOptionId. It has no textValue or customValue field to store user-typed text.
Admin side has ZERO API endpoints for Modifiers:
In src/routes/admin/product.routes.js, there is no endpoint to create, update, or delete modifier groups or options. Admin can only configure variants, not modifiers!
Order History does not record the chosen modifiers:
When an order is created, the final price includes the modifier total, but OrderItem in prisma/schema/order.prisma only stores title, sku, size, color, imageUrl, price, quantity, totalPrice. It does not store which modifier options (or custom text) were selected. The admin and customer cannot see whether the dress was ordered with the Gift Box or Monogram on the invoice!

Part 3: What We Need to Implement / Recommended Gaps
To bring your platform to true BigCommerce Catalyst standards and make it 100% production-ready for an upscale fashion e-commerce storefront, here are the concrete features we should add:

1. Full Catalyst-Style Modifier Upgrade (Priority 1)
Database Schema:
Add type enum to ModifierGroup: DROPDOWN, RADIO, CHECKBOX, TEXT, TEXTAREA.
Add textValue (string) to CartItemModifier.
Add modifiers JSON snapshot or OrderItemModifier to OrderItem so the custom choices (e.g. Gift Box: Yes, Monogram: "Priya") appear on the final order and invoice.
Admin API:
Add endpoints to create, update, and delete Modifier Groups and Options under a product:
POST /api/v1/admin/products/:id/modifiers
PUT /api/v1/admin/products/:id/modifiers/:groupId
DELETE /api/v1/admin/products/:id/modifiers/:groupId
Customer API:
Allow POST /api/v1/cart/items to accept both option IDs and custom text inputs:
json
"modifiers": [
  { "modifierOptionId": "uuid-for-gift-box" },
  { "modifierGroupId": "uuid-for-monogram", "textValue": "Ananya" }
]
2. Customer Return & Exchange Request API (Priority 2)
Currently, the database has statuses RETURN_REQUESTED, RETURNED, REFUNDED, and the admin can change the status.
Missing: A customer-facing endpoint:
POST /api/v1/orders/:orderNumber/return
Allows customer to select which items to return, choose a reason (e.g., "Size too small", "Defective piece"), and optionally upload a photo.
3. Order Tax Invoice / Receipt API (Priority 3)
An endpoint for both customer and admin:
GET /api/v1/orders/:orderNumber/invoice
Generates a clean HTML or downloadable summary with GST/tax breakdown, courier details, and item customizations.
4. Back-in-Stock / Restock Notification (Priority 4)
For fashion e-commerce, specific dress sizes (e.g., "Size S" or "Ivory White") often run out of stock.
A simple endpoint:
POST /api/v1/products/:id/notify-stock (customer enters email to be notified when the variant is restocked).
Summary Answer to Your Questions
Variants: Working as expected! Prices change dynamically based on the selected variant, stock is tracked per variant SKU, and both customer and admin have full variant support.
Modifiers: The price calculation works for predefined options, but it is not yet full Catalyst style: it lacks UI input types (dropdown vs checkbox vs text field), cannot accept custom user text (like embroidery/monograms), does not save the selected options onto the final order items, and has no Admin API to create them.
Overall API: Everything else (Auth, Catalog, Cart, Checkout, 4 Payment Gateways, Order Lifecycle, Tracking, Reviews, Wishlist, Inventory, Analytics) is solid, production-grade, and complete.
