# Database Schema Audit and Optimization

Act as a senior backend architect and database engineer. Thoroughly inspect my existing ecommerce project's database schema and identify what is necessary, unnecessary, redundant, inefficient, or missing.

## Primary Goal

Optimize the existing database structure for correctness, maintainability, performance, and long-term scalability without breaking any existing functionality.

## 1. Inspect the Entire Database

Inspect all relevant database files, including:

- Prisma schema files and all schema imports.
- Every model, table, field, enum, relation, and join table.
- Primary keys, foreign keys, unique constraints, indexes, defaults, and nullable fields.
- Migration history and existing database configuration.
- Backend services, controllers, repositories, and API routes that access these tables.
- Admin panel and customer-facing features that depend on database records.
- Any raw SQL queries, scheduled jobs, background workers, and external integrations that use the database.

Do not inspect the Prisma schema in isolation. Trace actual model usage throughout the codebase.

## 2. Identify Necessary and Unnecessary Tables

Classify every table/model into these categories:

- **Required:** Supports an existing business feature.
- **Potentially redundant:** May duplicate data or functionality already represented elsewhere.
- **Unused or legacy:** Appears unused, but requires further verification.
- **Missing or incomplete:** A model or relationship may be required for correctness, auditing, or reliability.
- **Requires business clarification:** Its purpose cannot be established confidently from the code.

For every table, explain its purpose, where it is used, which features depend on it, and the evidence supporting your classification.

Do not assume that a table is unnecessary just because it is not referenced directly in the frontend. It may be used by backend workflows, migrations, integrations, or historical records.

## 3. Inspect Relationships and Data Integrity

Check for:

- Duplicate or overlapping models.
- Incorrect or unnecessary relations.
- Missing foreign keys and unique constraints.
- Incorrect cascade-delete behavior.
- Orphaned records and inconsistent relationships.
- Fields that should be nullable or non-nullable.
- Incorrect data types, defaults, or enum values.
- Missing constraints that could allow duplicate orders, duplicate wishlist items, or invalid states.
- Whether historical order items preserve the purchased product name, price, quantity, and other necessary snapshots.
- Whether payment records and order status changes maintain data integrity.

Do not remove historical or financial records simply because they are no longer actively referenced.

## 4. Audit Database Indexes and Query Patterns

Inspect actual Prisma queries and SQL access patterns.

Identify:

- Missing indexes for frequently filtered, sorted, and joined fields.
- Duplicate or unnecessary indexes.
- Composite indexes that may improve common queries.
- Slow queries caused by fetching unnecessary relations or columns.
- N+1 query patterns.
- Inefficient pagination.
- Expensive admin dashboard aggregation queries.
- Unique constraints that should enforce business rules at the database level.

Recommend indexes based on real query patterns rather than adding an index to every field.

Consider index write overhead, storage cost, and the actual query planner behavior.

## 5. Verify Ecommerce Business Requirements

Check whether the existing schema correctly supports:

- Customer accounts, authentication, and addresses.
- Products, categories, variants, pricing, and inventory.
- Cart and wishlist operations.
- Order creation and order items.
- Payment status, payment references, and webhook idempotency.
- Shipping addresses and order status history, where required.
- Coupons, discounts, taxes, and shipping charges, if implemented.
- Admin management, audit history, and notifications.
- Background job tracking or an outbox, if required by the architecture.

Do not introduce new tables just because they are common in ecommerce applications. Add them only when justified by existing requirements or a clearly documented reliability need.

## 6. Migration Safety

Review the existing migration history before recommending schema changes.

For every proposed change, specify:

- Why it is necessary.
- Which existing features could be affected.
- Whether it can cause data loss.
- Whether existing data requires cleanup or backfilling.
- Whether a migration is needed.
- Whether the change should be deployed in multiple backward-compatible stages.
- How to verify the migration and roll back safely where possible.

Never reset the database, delete migrations, drop tables, remove fields, or run destructive commands without my explicit approval.

## 7. Required Output

Produce a clear report containing:

1. Current database architecture overview.
2. Complete table/model inventory and usage evidence.
3. Required, redundant, potentially unused, and missing model classifications.
4. Relationship and data-integrity issues.
5. Index and query optimization recommendations.
6. A prioritized list of proposed changes with impact and risk.
7. A safe migration plan, including backup and verification requirements.
8. A testing plan to confirm existing features still work.

Separate confirmed findings from assumptions and recommendations.

## Strict Instructions

- This is an existing production-oriented project. Preserve current functionality.
- Do not modify code, schema files, migrations, or database data during this initial audit.
- Do not delete or rename tables or fields based on assumptions.
- Do not invent models or requirements without evidence.
- If a recommendation requires clarification, explain exactly what needs clarification.
- Be specific: reference actual file paths, model names, relations, and query locations.
- Finish with the recommended implementation order, starting with the highest-impact, lowest-risk improvements.

First complete the audit and present the report. Wait for my approval before implementing any changes.
