# E-commerce Customer-Side Category & Product APIs

We are building a large, production-quality e-commerce backend using:

* Node.js
* TypeScript
* PostgreSQL
* Prisma ORM
* Neon PostgreSQL
* Render.com

The authentication APIs have already been/will be implemented separately.

Now we need to build the **customer-facing category and product discovery APIs**.

This task is ONLY for the **customer/client side**.

Do NOT implement the admin APIs yet.

After the entire customer-side API is completed, we will build the admin side separately.

# 2. IMPORTANT ARCHITECTURE DECISION

### DO NOT COMBINE CATEGORY AND PRODUCT APIs.

Category APIs and Product APIs must remain separate.

The category page needs lightweight product information for browsing.

The product details page needs the complete product information.

Therefore:

```text
Category API
    ↓
Category information
    ↓
Subcategories
    ↓
Product listing summaries
    ↓
Basic pricing
    ↓
Filters
    ↓
Sorting
    ↓
Pagination
```

While:

```text
Product API
    ↓
Complete product details
    ↓
All images
    ↓
Variants
    ↓
Variant attributes
    ↓
Modifiers
    ↓
Complete pricing
    ↓
Product attributes
    ↓
Wishlist information
    ↓
Other product information
```

Do not return the entire product object from category listing APIs.

# 4. CATEGORY STRUCTURE

Categories must support hierarchical nesting.

Do NOT hardcode only:

```text
Category
Subcategory
Sub-subcategory
Sub-sub-subcategory
```

Instead, use a self-referencing category relationship.

Example:

```text
Electronics
 └── Computers
      └── Laptops
           └── Gaming Laptops
                └── Accessories
```

There may currently be 3–4 levels, but the database design should support additional levels without requiring a schema redesign.

Conceptually:

```text
Category
├── id
├── name
├── slug
├── imageUrl
├── parentId
├── sortOrder
├── isActive
├── createdAt
└── updatedAt
```

Follow the existing schema if equivalent fields/models already exist.

Do not blindly create duplicate fields.

# 12. PRICING ARCHITECTURE

Pricing is extremely important.

Use a clean, extensible pricing model.

For the customer-facing product price, support these three price levels:

```text
1. Regular Price
2. Sale Price
3. Offer Price
```

### Regular Price

The normal/base selling price.

Example:

```text
₹2,000
```

### Sale Price

A reduced product price.

Example:

```text
Regular: ₹2,000
Sale: ₹1,600
```

### Offer Price

A special product-level offer price.

Example:

```text
Regular: ₹2,000
Sale: ₹1,600
Offer: ₹1,400
```

The API should expose the applicable pricing clearly.

For example:

```json
{
  "regular": 2000,
  "sale": 1600,
  "offer": 1400,
  "effective": 1400,
  "discountPercentage": 30
}
```

If a particular price does not exist, return `null` rather than fake values.
