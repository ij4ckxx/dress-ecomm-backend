# Token Cleanup Cron Job Specification & Architecture

**Document Reference:** `document/20.cron_job.md`  
**Target Audience:** Backend Developers, DevOps Engineers & System Maintainers  
**Module:** Background Jobs / Database Maintenance  
**Package:** `node-cron`  
**Configuration Key:** `TOKEN_CLEANUP_CRON` (in `.env`)  

---

## 1. Executive Summary & Objective

In modern token-based authentication with refresh token rotation:
1. **Access Tokens** (`JWT`) are short-lived (15 minutes by default) and **stateless** — they are signed cryptographically and **never stored in the database**.
2. **Refresh Tokens** (`RefreshToken` table) are long-lived (7 days by default) and **stored hashed in PostgreSQL** to facilitate session tracking, single-device logout, and security revocation.
3. **Password Reset Tokens** (`PasswordResetToken` table) are short-lived tokens (1 hour expiration) stored in the database for account recovery flows.

### The Problem
In real-world e-commerce usage, users rarely click "Log Out" before leaving the website or closing browser tabs. As tokens naturally expire or become revoked, stale rows accumulate indefinitely in the database, leading to:
- Unnecessary database storage bloat.
- Degraded query performance on indexed token lookups over time.
- Clutter when inspecting user accounts or running audits.

### The Solution
An automated, resilient background cron job running on an isolated interval (default: **every 6 hours**) that automatically purges all expired or revoked tokens without requiring manual database administration.

---

## 2. Affected Database Tables

The cleanup job targets two specific tables in the PostgreSQL database:

| Model / Table | File Path | Purge Condition | Expiration Window |
| :--- | :--- | :--- | :--- |
| **`RefreshToken`** | `prisma/schema/auth.prisma` | `expiresAt < NOW()`<br>**OR**<br>`revokedAt IS NOT NULL` | 7 days (`JWT_REFRESH_EXPIRES_IN`) |
| **`PasswordResetToken`** | `prisma/schema/auth.prisma` | `expiresAt < NOW()` | 1 hour from creation |

> [!NOTE]
> **Access Tokens are NOT stored in the database.**  
> Access tokens are verified purely via cryptographic signature in memory using `JWT_ACCESS_SECRET`. Therefore, no database rows exist for access tokens and no cleanup is needed.

## 4. Implementation Details

### 4.1 Core Job Module (`src/jobs/tokenCleanup.job.js`)

The cron job is encapsulated using pure functional exports:

1. **`cleanupExpiredTokens()`**
   - Retrieves the current timestamp (`now = new Date()`).
   - Executes `prisma.refreshToken.deleteMany(...)` targeting:
     ```javascript
     where: {
       OR: [
         { expiresAt: { lt: now } },
         { revokedAt: { not: null } },
       ],
     }
     ```
   - Executes `prisma.passwordResetToken.deleteMany(...)` targeting:
     ```javascript
     where: {
       expiresAt: { lt: now },
     }
     ```
   - Logs the exact count of purged rows only if `count > 0` (preventing console log noise when database is clean).
   - Catches and logs errors without crashing the server process.

2. **`startTokenCleanupCron()`**
   - Validates the cron expression from `ENV.TOKEN_CLEANUP_CRON` using `cron.validate()`.
   - Falls back gracefully to `'0 * * * *'` (hourly) if an invalid cron format is provided in `.env`.
   - **Immediate Boot Execution:** Runs `cleanupExpiredTokens()` immediately when the server starts up to clean any tokens that expired while the server was down/deploying.
   - Schedules recurring executions using `cron.schedule()`.

3. **`stopTokenCleanupCron()`**
   - Safely stops the cron runner during server termination.

### 4.2 Server Lifecycle Integration (`src/server.js`)

The cron job is tied directly to the Express server lifecycle:

- **Startup:** Initialized inside `app.listen()` callback:
  ```javascript
  const server = app.listen(PORT, () => {
    console.log(`Server listening on port ${PORT}`);
    startTokenCleanupCron();
  });
  ```
- **Graceful Shutdown:** Stops the cron task on `SIGTERM` and `SIGINT`:
  ```javascript
  process.on('SIGTERM', () => {
    console.log('SIGTERM signal received. Closing HTTP server and stopping cron jobs...');
    stopTokenCleanupCron();
    server.close(() => {
      console.log('HTTP server closed.');
      process.exit(0);
    });
  });
  ```

## 5. Environment Variable Configuration

The cron schedule is configurable via environment variables in `.env` without modifying application code:

```env
# Cron Schedule for Expired Token Cleanup (Default: every 6 hours)
TOKEN_CLEANUP_CRON="0 */6 * * *"
```

### Common Cron Expressions Reference:

| Expression | Meaning | Typical Use Case |
| :--- | :--- | :--- |
| `0 */6 * * *` | **At minute 0 every 6 hours** (00:00, 06:00, 12:00, 18:00) | **Default / Recommended** for balance between DB load and cleanliness |
| `0 * * * *` | At minute 0 of every hour | High-traffic applications with frequent logins |
| `0 */12 * * *` | At minute 0 every 12 hours | Moderate traffic sites |
| `0 0 * * *` | Once a day at midnight (00:00 UTC) | Low traffic / development |

### Validation & Fallback Safety:
If a developer enters an invalid cron string (e.g. `TOKEN_CLEANUP_CRON="invalid_cron"`), `node-cron` validation catches it, logs a warning, and falls back to `'0 * * * *'` without crashing the application.

## 6. How to Test & Verify

### 6.1 Automatic Verification on Server Startup
Whenever nodemon restarts or when you run `npm run dev`, watch the server console:
```bash
Server listening on port 5000
[CRON] Cleaned up 32 expired/revoked refresh token(s) and 0 expired reset token(s).
[CRON] Token cleanup cron scheduled successfully with expression: '0 */6 * * *'
```

### 6.2 Manual Verification Script (CLI)
You can trigger the cleanup function directly from the terminal at any time without waiting for the scheduled time:

```bash
node -e "import('./src/jobs/tokenCleanup.job.js').then(m => m.cleanupExpiredTokens()).then(r => { console.log('Result:', r); process.exit(0); });"
```

### 6.3 Database Inspection via Prisma Studio
To inspect remaining active tokens in your database:
```bash
npx prisma studio
```
Navigate to the **`RefreshToken`** table:
- Every existing row should have `expiresAt > NOW()`.
- Every existing row should have `revokedAt = null`.

## 7. Performance & Production Considerations

1. **Lightweight Query:**  
   The delete query uses indexed timestamp columns (`expiresAt`), making deletion fast even on millions of records.
2. **Zero In-Memory Overhead:**  
   `node-cron` uses a simple JavaScript timer loop in the background process, consuming negligible CPU and RAM.
3. **Multi-Instance / Cluster Deployments:**  
   If deploying across multiple horizontal containers (e.g., multiple Render instances or Kubernetes pods):
   - Running the job across multiple instances is safe because `deleteMany` is idempotent (`WHERE expiresAt < NOW()`). If instance A deletes the expired tokens, instance B will simply find 0 matching rows and do nothing.
   - For ultra-high scale, this can also be extracted into an independent Render Cron Job or Cloudflare Worker hitting a protected internal endpoint.
