# Wishlist — Final Clarifications and BigCommerce-Inspired Requirements

Update `document/14.wishlist_prompt.md` with the following confirmed decisions and implementation requirements. Follow BigCommerce's general wishlist experience while adapting it to our existing e-commerce project architecture.

## 1. Guest Wishlist vs. Authenticated Customers

Wishlist functionality must be available only to authenticated customers.

* Guests must log in or register before adding products to their wishlist.
* Use the existing authentication mechanism and authorization middleware.
* Do not introduce guest wishlist tokens, local-storage wishlist persistence, or guest-to-customer wishlist synchronization.
* After successful login, return the customer to the intended page or action where appropriate.
* Each customer's wishlist must remain private and persistent across sessions and devices.
* Enforce wishlist ownership on the backend for every read, create, update, and delete operation.

## 2. Product-Level vs. Variant-Level Wishlist

Follow the general BigCommerce-style behavior of saving products to a wishlist rather than requiring customers to select a size or color before saving.

Our existing Prisma schema already contains `Wishlist` and `WishlistItem` models in `prisma/schema/catalog.prisma`. Inspect their relations and existing API implementation before making any database changes.

* Save wishlist items at the product level using `productId`.
* Do not require a specific size, color, or variant to save a product.
* Display current product information, including available sizes, colors, price, and availability, wherever supported by the existing product catalogue.
* Let customers select the appropriate variant when adding a wishlisted product to the cart, if the product requires variant selection.
* If variant-specific wishlisting is already implemented elsewhere, inspect it before deciding whether any migration is necessary. Do not introduce an optional `variantId` without a clear requirement.

## 3. Wishlist-to-Cart Behavior

Provide an Add to Cart action for eligible wishlist products using the existing cart APIs and business logic.

* Validate the current product, selected variant, price, and inventory.
* If a product requires size or color selection, ask the customer to select the required options before adding it to the cart.
* Handle unavailable and out-of-stock products appropriately.
* Update the cart count and relevant UI state after a successful operation.
* Adding a product to the cart must not automatically remove it from the wishlist.
* If a dedicated Move to Cart action is implemented later, remove the wishlist entry only after the cart operation succeeds.
* Do not duplicate cart functionality or create a separate cart implementation for wishlist products.

## 4. Admin Wishlist Analytics

Prioritize the customer-facing wishlist functionality first.

Inspect the existing admin architecture to determine whether product interest or wishlist analytics can be added without unnecessary changes.

If it fits the existing architecture, provide an admin-only overview of useful metrics, such as:

* Total wishlist entries.
* Number of customers with wishlists.
* Most-wishlisted products.
* Wishlist counts by product or category, where the required data exists.

Do not expose individual customers' private wishlist information unnecessarily. Restrict analytics to authorized admin users and avoid collecting redundant data or building an unrelated analytics system.

If this functionality requires substantial additional work, document it as a separate future enhancement instead of delaying the core wishlist implementation.

## 5. Existing Database Schema

The following models already exist in `prisma/schema/catalog.prisma`:

* `Wishlist`: `id`, `userId` with a unique constraint, `createdAt`, `updatedAt`, and `items WishlistItem[]`.
* `WishlistItem`: `id`, `wishlistId`, `productId`, `createdAt`, and a unique constraint on `[wishlistId, productId]`.

Reuse these models and their existing relations wherever possible.

Do not recreate existing models, duplicate tables, or modify the database schema unnecessarily. Inspect the current implementation, migrations, and indexes before deciding whether changes are required.

## 6. Implementation Requirements

Inspect the existing project and implement the wishlist page with backend pagination, sorting, supported filters, search, product navigation, wishlist actions on PDP/category/search and other relevant shared product cards, and Add to Cart integration.

Use the existing authentication, product, cart, API, UI, and state management patterns. Keep wishlist state synchronized across pages, prevent duplicate entries, handle loading and error states, and ensure that each customer can access only their own wishlist.

Do not break existing functionality or perform unrelated refactoring. Before coding, identify the files and APIs that need changes. After implementation, report the modified files, database changes, APIs created or reused, tests performed, and any remaining limitations.

**Final instruction:** Follow BigCommerce's general customer wishlist experience while preserving our existing architecture. Inspect first, reuse existing models, avoid unnecessary migrations, and implement the feature safely without breaking existing code.
