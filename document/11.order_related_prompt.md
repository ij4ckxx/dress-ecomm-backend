# Implement Order Confirmation, Order History, Order Details, and Order Metafields

We are now going to implement the order management flow for our existing dress e-commerce project, following the general user experience and functionality of BigCommerce.

## 1. First, Understand the Existing Project

Before making any changes, carefully inspect the existing codebase, folder structure, checkout flow, authentication system, database schema, API routes, reusable components, UI theme, and coding conventions.

Understand how checkout currently works, how products and addresses are stored, how the logged-in customer is identified, and how orders can be created and retrieved.

**Critical instructions:**

* Do not break, remove, rewrite, or unnecessarily modify any existing functionality.
* Do not redesign or change the existing checkout page.
* Reuse existing components, utilities, services, API patterns, database models, and styling wherever possible.
* Follow the existing folder structure and coding conventions.
* Do not duplicate code unnecessarily. Create reusable components where appropriate.
* Do not introduce new dependencies, database models, or theme variables without first checking whether existing solutions can be reused.
* If a required feature conflicts with existing code or requires a significant architectural change, explain the issue and propose the safest solution before proceeding.
* Implement the feature in small, logical steps and verify that existing functionality continues to work.

## 2. Order Confirmation Page

After checkout is successfully completed and the order is actually created, redirect the customer to the Order Confirmation page.

The page should provide a clear confirmation message and display the following information:

* Order number and order placement date.
* Order status and payment status.
* Complete list of purchased products, including product images, names, selected sizes, colors, quantities, and prices wherever applicable.
* Item subtotal, discounts, coupon details, shipping charges, taxes, and final order total, according to the existing pricing implementation.
* Shipping address and billing address, where applicable.
* Shipping method and payment method.
* Estimated delivery date or delivery information, if supported by the existing system.
* A button or link to view the complete order details.
* A button to continue shopping.

Make the page responsive and consistent with the existing checkout UI and theme.

Do not trust prices, totals, or order details submitted directly by the frontend. Use the backend's validated order data as the source of truth.

The confirmation page must retrieve the actual created order. Refreshing the page must not create a duplicate order. Handle loading, errors, and invalid order access appropriately.

## 3. Customer Order History Page

When a customer logs in and opens the account section, provide an Order History page listing their previous orders.

Display each order in a minimal, clean, easy-to-scan format, including:

* Order number.
* Order date.
* Product thumbnail or a small product preview.
* Product name or a concise summary of the purchased items.
* Number of items.
* Total order amount.
* Current order status.
* Payment status.
* A View Order Details action.

Keep the order list compact and user-friendly. If an order contains multiple products, show a minimal preview instead of displaying every product's complete information in the list.

Support pagination if appropriate for the existing project. Include proper loading, empty, and error states.

Customers must only be able to view their own orders. Enforce this restriction on the backend, not just in the frontend.

## 4. Particular Order Details Page

When the customer clicks an order in Order History or selects View Order Details from the confirmation page, navigate to a dedicated page for that particular order.

Follow the general order details experience of BigCommerce, adapted to our existing project.

The page should display:

**A. Order information**

* Order number.
* Order placement date and relevant timestamps.
* Current order status and status history, if supported.
* Payment status and payment method.
* Shipping method and tracking number or tracking link, if available.

**B. Purchased products**

* Product image and product name.
* Product variant details, such as size and color.
* SKU, if available.
* Quantity and unit price.
* Discounts and applicable item-level pricing.
* Line-item totals.
* Product-level order metafields, where applicable.

Preserve the product and variant information as it existed when the order was placed. Do not rely exclusively on the current product catalogue, because product names, prices, variants, or availability may change later.

**C. Pricing summary**

* Subtotal.
* Item-level and order-level discounts.
* Coupon or promotion details.
* Shipping charges.
* Taxes, if applicable.
* Final order total.
* Refund amount and refund status, if applicable.

Avoid calculating order totals differently from the existing checkout and backend pricing logic.

**D. Addresses and delivery**

* Shipping address.
* Billing address, where applicable.
* Shipping method.
* Fulfilment status.
* Estimated delivery information, if supported.
* Shipment tracking information, if available.

Store or retrieve the appropriate order-time address snapshot so that changes to the customer's saved address do not unexpectedly alter historical order details.

**E. Additional actions**

* Return to Order History.
* Continue shopping.
* Reorder, if the existing product and cart functionality supports it.
* Download or print an order invoice, if invoice functionality is already available or can be implemented safely.
* Display cancellation, return, or refund actions only if the corresponding backend workflows exist. Do not create non-functional buttons.

## 5. Order Status and Payment Status

Design the order status handling so that customers can understand the current state of their order.

Review the existing implementation before defining or changing status values. Where supported, handle statuses such as:

* Pending.
* Awaiting payment.
* Confirmed or awaiting fulfilment.
* Processing.
* Shipped.
* Delivered.
* Cancelled.
* Partially refunded or refunded.

Keep payment status separate from fulfilment/order status. For example, a paid order is not necessarily shipped, and a cancelled order may still require a refund.

Do not automatically mark an order as paid, shipped, or delivered without the appropriate verified backend event or payment/shipping integration. Use the project's existing status conventions and transition rules wherever possible.

If status history is implemented, record the status change, timestamp, and relevant details so that the order details page can show an accurate timeline.

## 6. Order Metafields — BigCommerce-Style Design

We want an order metafield system similar in concept to BigCommerce, allowing us to attach additional structured data to an order without continuously adding new columns to the main Order model.

First inspect the existing Prisma schema, database models, and metadata patterns. If no suitable implementation exists, propose and implement a reusable order metafield model appropriate for the current architecture.

The design should support:

* An order identifier associated with each metafield.
* Namespace or grouping key.
* Metafield key.
* Value.
* Value type or a suitable structured-value representation.
* Description, if needed.
* Creation and update timestamps.
* Appropriate uniqueness constraints and database indexes.

For example, an order might have metafields such as:

* `delivery.instructions`
* `delivery.gift_message`
* `customer.source`
* `fulfillment.warehouse_reference`
* `integration.external_order_id`

These are illustrative examples, not mandatory fields to add to every order.

Use a secure and maintainable design. Validate metafield keys, namespaces, value types, and payload sizes. Avoid storing duplicate order information that already belongs in dedicated order fields or tables.

Do not expose sensitive internal metadata to customers. Separate customer-visible metadata from private operational or integration metadata through explicit authorization and API response filtering.

The implementation should support retrieving order metafields with a particular order and, where appropriate, creating or updating them through authorized backend operations.

Do not copy BigCommerce's proprietary implementation. Reproduce the relevant general functionality using our own existing architecture and coding conventions.

## 7. Backend APIs and Database Integrity

Inspect the existing APIs before adding new ones. Reuse suitable endpoints and services instead of creating duplicates.

Implement only the endpoints required for the feature, following the project's existing route and response conventions. Depending on the current architecture, these may include:

* Retrieve the current customer's order history.
* Retrieve one particular order belonging to the authenticated customer.
* Retrieve order items, pricing snapshots, addresses, and permitted metafields.
* Create or update permitted order metafields.
* Retrieve order status history, if supported.

Ensure that:

* All order access is authorized on the backend.
* Customers cannot access another customer's order by changing an order ID.
* Order creation and associated order items are saved consistently using database transactions where appropriate.
* Duplicate order creation is prevented during checkout retries.
* Historical order prices, variants, totals, and addresses remain accurate.
* Metafields cannot be used to override trusted order totals, payment status, or authorization rules.
* Existing authentication, cart, product, address, and checkout APIs continue to work.
* Errors are handled consistently with the existing backend patterns.

## 8. Frontend Structure and Code Quality

Follow the existing frontend folder structure and theme. Reuse the existing layout, buttons, cards, typography, badges, address components, product cards, and other UI elements wherever appropriate.

Create separate, reusable components for the order confirmation, order history, order summary, purchased items, pricing summary, address sections, status display, and metafield presentation when it makes sense.

Keep the implementation simple, maintainable, responsive, and easy for another developer to understand. Avoid repeated JSX, duplicated business logic, unnecessary abstractions, and hardcoded theme colors.

Do not modify unrelated pages, including the existing checkout page, authentication pages, product pages, wishlist, or cart, unless a specific integration change is necessary. If any change is necessary, keep it minimal and backward-compatible.

## 9. Implementation and Verification

Before coding, report your understanding of the existing checkout-to-order flow, identify the files and models that need changes, and describe the implementation plan.

Then implement the feature using the existing architecture.

After implementation, verify:

* Successful checkout redirects to the correct order confirmation page.
* Refreshing the confirmation page does not create another order.
* Order history displays the authenticated customer's orders.
* Selecting an order displays the correct order details.
* Another customer cannot access that order.
* Product, variant, address, pricing, and payment information is accurate.
* Order metafields can be stored and retrieved securely.
* Status information is consistent with the backend.
* Empty states, loading states, invalid orders, and API errors are handled correctly.
* Existing cart, checkout, authentication, product, and account functionality remains intact.
* Existing tests pass, and relevant tests are added or updated.

Do not assume an integration exists simply because a UI element would be useful. If payment verification, shipment tracking, refunds, invoices, or other functionality is not supported by the current project, clearly identify the limitation and implement only what can be supported reliably.

**Final requirement:** Build a complete, maintainable order management experience inspired by BigCommerce while preserving our existing codebase. Inspect first, reuse existing functionality, avoid breaking changes, and report the files changed, database migrations required, APIs implemented, and tests performed.
