## 1. Overview & Architecture

The Inventory & Stock Ledger engine safeguards luxury garment availability, eliminates overselling, and maintains an unalterable audit trail for warehouse reconciliations:

1. **Variant-Level Granularity:**
   - Fashion stock is tracked at the individual variant level (`Size: M`, `Color: Navy`, `SKU: MSG-001-M`).
   - Standalone product stock is automatically synchronized with the sum of its active variants.
2. **Double-Entry Audit Ledger (`InventoryTransaction`):**
   - Every stock change creates an immutable audit row recording:
     - `previousStock`, `newStock`, `quantityChange` (+/-)
     - `type`: `RESTOCK`, `SALE`, `ADJUSTMENT`, `RETURN`, `DAMAGE`
     - `reason`: Mandatory explanatory text (e.g., "Supplier Shipment PO-9810", "Damaged in fitting room")
     - `referenceId`: Optional supplier invoice, PO number, or customer RMA
     - `createdById`: Admin user who authorized the change
3. **Safety Stock & Intelligent Alerts:**
   - Each variant/product can have an individual `lowStockThreshold` (Default: `5` units).
   - Real-time stock status is computed dynamically:
     - `IN_STOCK`: `stockQuantity > lowStockThreshold`
     - `LOW_STOCK`: `0 < stockQuantity <= lowStockThreshold`
     - `OUT_OF_STOCK`: `stockQuantity === 0`
4. **Atomic Safety & Race Condition Protection:**
   - Adjustments execute inside isolated database transactions (`prisma.$transaction`).
   - Prevents negative stock exceptions (`calculatedStock < 0` immediately rejects).

## 2. API Endpoints Specification

### 2.1. Get Flattened Inventory Monitoring Table
Retrieves all inventory items flattened by garment SKU/variant with real-time stock counters and warehouse status summary cards.

- **Endpoint:** `GET /api/v1/admin/inventory`
- **Headers:** `Authorization: Bearer <token>`
- **Query Parameters:**
  - `page`: Page number (Default: `1`)
  - `limit`: Items per page (Default: `20`, Max: `100`)
  - `search`: Searches across SKU, variant name, parent product name, and brand
  - `status`: `"ALL"` (default), `"IN_STOCK"`, `"LOW_STOCK"`, `"OUT_OF_STOCK"`
  - `categoryId`: Filter by specific category UUID
  - `sort`: `"stock_asc"` (default, most critical first), `"stock_desc"`, `"name_asc"`, `"sku_asc"`, `"newest"`
- **Example Request:**

### 2.2. Adjust Stock (Atomic Stock Update & Audit Log)
Modifies the inventory level for a variant or standalone product and creates an audit entry in the inventory ledger.

- **Endpoint:** `POST /api/v1/admin/inventory/adjust`
- **Headers:** `Authorization: Bearer <token>`, `Content-Type: application/json`
- **Request Body Fields:**
  - `variantId` (UUID, optional*): ID of the garment variant to adjust
  - `productId` (UUID, optional*): ID of the standalone product to adjust (*either `variantId` or `productId` is required)
  - `delta` (Integer, optional**): Relative change, e.g. `+15` (shipment received) or `-3` (damaged)
  - `newStock` (Integer, optional**): Absolute target count, e.g. `20` (**either `delta` or `newStock` is required)
  - `type` (Enum, optional): `"RESTOCK"`, `"SALE"`, `"ADJUSTMENT"` (default), `"RETURN"`, `"DAMAGE"`
  - `reason` (String, required): Explanatory reason (3 - 500 characters)
  - `referenceId` (String, optional): Purchase Order number, receipt ID, or supplier bill
- **Example Request Body (Restock shipment by delta):**
```json
{
  "variantId": "var_uuid_001",
  "delta": 20,
  "type": "RESTOCK",
  "reason": "Received Autumn Batch replenishment from Milan warehouse",
  "referenceId": "PO-2026-9812"
}
```
- **Example Request Body (Physical count reconciliation by newStock):**
```json
{
  "variantId": "var_uuid_001",
  "newStock": 18,
  "type": "ADJUSTMENT",
  "reason": "Physical cycle count discrepancy audit",
  "referenceId": "AUDIT-OCT-2026"
}
```
- **Response `200 OK`:**
```json

  "statusCode": 200,

  "data": {

      "variantId": "var_uuid_001",
      "productId": "prod_uuid_101",
      "type": "RESTOCK",
      "quantityChange": 20,
      "previousStock": 2,
      "newStock": 22,
      "reason": "Received Autumn Batch replenishment from Milan warehouse",
      "referenceId": "PO-2026-9812",
      "createdAt": "2026-10-10T01:30:00.000Z",
```

## 3. Frontend Implementation & UI Guidelines

### 3.1. Warehouse Summary Metric Cards
Use `meta.summary` from `GET /api/v1/admin/inventory` to populate the top cards:
- **Total SKU Count:** `summary.totalVariants`
- **Total Physical Units:** `summary.totalStockUnits`
- **Low Stock Warnings:** `summary.lowStockCount` (Amber badge)
- **Out of Stock:** `summary.outOfStockCount` (Crimson red badge)

### 3.2. Stock Status Badges
| Status | Condition | Recommended UI Badge |
| :--- | :--- | :--- |
| `IN_STOCK` | `stockQuantity > lowStockThreshold` | Emerald Green (`bg-emerald-50 text-emerald-700`) |
| `LOW_STOCK` | `stockQuantity <= lowStockThreshold && stockQuantity > 0` | Amber / Warning (`bg-amber-50 text-amber-700`) |
| `OUT_OF_STOCK` | `stockQuantity === 0` | Crimson Red (`bg-rose-50 text-rose-700`) |

### 3.3. Stock Adjustment Modal Flow
When the store manager clicks **"Adjust Stock"** on any row:
1. Render a clean modal showing the garment's Thumbnail, SKU, Product Name, and **Current Stock**.
2. Provide two input modes via toggle tab:
   - **Relative Adjustment (Delta):** User types `+10` or `-2`.
   - **Count Reconciliation (New Stock):** User types absolute count `25` (automatically calculates the delta).
3. Select Transaction Type:
   - Restock (`RESTOCK`)
   - Manual Inventory Adjustment (`ADJUSTMENT`)
   - Fitting Room / Warehouse Damage (`DAMAGE`)
   - Customer Store Return (`RETURN`)
4. Input mandatory **Reason** (e.g., "Supplier PO #1234 delivery") and optional **PO/Reference ID**.
5. On submit, immediately update the table row optimistically or refetch `GET /api/v1/admin/inventory`.
