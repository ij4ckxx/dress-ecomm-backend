# Implement Customer Account Details API

## Project Context

I am building a dress e-commerce application. The existing project already has authentication and customer functionality.

After a customer logs in successfully, they can access the customer account page, which contains four sections:

* Orders
* Account Details
* Addresses
* Wishlist

For now, implement **only the Account Details APIs**. We will implement Addresses CRUD separately in the next phase.

## Step 1: Inspect the Existing Project

Before making any changes:

1. Inspect the existing backend structure, routes, controllers, services, middleware, database schema, validation, authentication, and error-handling patterns.
2. Identify how the authenticated customer is represented and how the current user ID is obtained.
3. Check the existing customer/user model and authentication implementation.
4. Reuse existing functions and conventions wherever possible.
5. Identify potential conflicts or database changes before modifying anything.

**Do not rewrite existing authentication or introduce a duplicate customer model. Do not break any existing functionality.**

If a proposed change requires modifying existing functionality or the database schema, explain the reason and proposed changes before proceeding.

## Step 2: Account Details API

Create an API that allows an authenticated customer to retrieve their account details and update their profile.

### Fields

* `firstName` — required
* `lastName` — required
* `email` — required
* `phoneNumber` — optional

### Requirements

1. Implement an API to retrieve the currently authenticated customer's account details.
2. Implement an API to update the customer's account details.
3. Only allow customers to read and update their own information.
4. Obtain the customer ID from the authenticated session/token middleware, not from an arbitrary client-supplied user ID.
5. Validate required fields on the backend.
6. Validate email format.
7. Normalize email addresses consistently with the existing authentication logic.
8. If the email changes, check for duplicates and preserve the existing unique-email constraints.
9. Follow the project's existing email-verification and authentication rules. Do not silently bypass email verification or change login behavior.
10. Validate the phone number when supplied, using appropriate rules consistent with the existing project.
11. Handle missing fields, invalid data, duplicate emails, unauthenticated requests, and unexpected server errors consistently with the existing API conventions.
12. Do not return passwords, password hashes, tokens, or other sensitive authentication data.
13. Use appropriate HTTP status codes and consistent response structures.
14. Avoid overwriting existing values with `undefined`, `null`, or empty strings unintentionally.
15. Use database transactions when needed and follow the existing ORM/database access patterns.

### API Design

Follow the project's existing route naming and response conventions. A possible design is:

* `GET /api/customer/account` — retrieve account details.
* `PATCH /api/customer/account` — update account details.

Treat these as proposed paths, not mandatory replacements for existing routes. Check for conflicts before choosing the final endpoints.

## Step 3: Change Password API

Implement a separate API for changing the authenticated customer's password.

### Fields

* `currentPassword` — required
* `newPassword` — required

### Requirements

1. Verify the current password against the stored password hash using the existing password-hashing library.
2. Never compare plaintext passwords with stored hashes directly.
3. Validate the new password according to the existing password policy. If no policy exists, propose a reasonable policy before implementing it.
4. Hash the new password using the existing password-hashing approach.
5. Never return or log passwords or password hashes.
6. Return a clear validation error when the current password is incorrect.
7. Do not allow unauthenticated customers to change passwords.
8. Consider invalidating existing sessions or refresh tokens after a successful password change, following the project's existing authentication design.
9. Do not accidentally change the customer's email, profile details, or unrelated authentication behavior.

Proposed endpoint: `PATCH /api/customer/account/password`.

Inspect the existing project before finalizing the route and implementation.

## Step 4: Admin Configurability

In the future, I want the admin panel to be able to configure which account fields are required or optional.

For this implementation:

* Do not build the admin UI or a new configuration system yet.
* Keep validation organized so it can be extended safely.
* Explain whether configurable validation requires a database schema, configuration table, or other architectural changes.
* Do not make security-critical fields, authentication rules, or database constraints freely configurable without discussing the consequences.

## Step 5: Testing

Test the following scenarios:

* Authenticated customer retrieves their account details.
* Customer updates valid profile information.
* Customer submits missing required fields.
* Customer submits an invalid email.
* Customer attempts to use an email already belonging to another account.
* Unauthenticated customer attempts to access these APIs.
* Customer attempts to update another customer's information.
* Customer changes their password with the correct current password.
* Customer supplies an incorrect current password.
* Customer supplies an invalid new password.
* Existing login and authentication functionality continues to work.

Add automated tests using the testing framework already present in the project. Do not introduce a new testing framework unnecessarily.

## Step 6: Final Report

After implementation, report:

1. Files created and modified.
2. APIs and request/response examples.
3. Validation rules implemented.
4. Database changes, if any.
5. Tests performed and their results.
6. Any existing functionality that needed modification and why.
7. Any security considerations or unresolved issues.
8. Recommended next steps for the Addresses API.

**Important:** Implement only Account Details and Change Password in this phase. Do not implement Addresses, Orders, Wishlist, or unrelated features. Preserve all existing functionality.
