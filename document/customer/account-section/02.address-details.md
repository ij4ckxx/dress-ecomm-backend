# Implement Customer Addresses CRUD API

## Project Context

This is the next phase of my existing dress e-commerce application.

The Customer Account Details API has been implemented separately. Now I want to implement **customer address management with complete CRUD operations**.

The customer should be able to create multiple addresses, view saved addresses, update an address, and delete an address.

Before making changes, inspect the existing project and reuse the current authentication, database, validation, routing, controller, service, and error-handling patterns.

**Do not break the existing Account Details API, Change Password API, authentication, or any other existing functionality.**

## Step 1: Address Data Model

Each address should support the following fields:

* `firstName` — required
* `lastName` — required
* `address1` — required
* `address2` — optional
* `country` — required
* `state` — required
* `city` — required
* `postalCode` — required
* `phoneNumber` — optional
* `company` — optional

Use `firstName` and `lastName` rather than a single `fullName` field because this supports structured customer information and can be reused for shipping labels and checkout forms.

If the existing project has an established address model or naming convention, inspect it before deciding whether a schema change is necessary.

## Step 2: CRUD APIs

Implement the following operations using the project's existing route conventions.

### 1. Create Address

Proposed endpoint: `POST /api/customer/addresses`

Requirements:

* Create an address for the authenticated customer.
* Validate all required fields on the backend.
* Allow optional fields to be omitted.
* Associate the address with the authenticated customer's ID.
* Do not accept an arbitrary customer ID from the request to determine ownership.
* Return the newly created address.

### 2. Get All Addresses

Proposed endpoint: `GET /api/customer/addresses`

Requirements:

* Return the authenticated customer's saved addresses.
* Never return another customer's addresses.
* Return an appropriate empty array when the customer has no saved addresses.
* Use a consistent response structure.

### 3. Get One Address

Proposed endpoint: `GET /api/customer/addresses/:addressId`

Requirements:

* Retrieve a single address only if it belongs to the authenticated customer.
* Return the project's standard not-found response when the address does not exist or does not belong to the customer.

### 4. Update Address

Proposed endpoint: `PATCH /api/customer/addresses/:addressId`

Requirements:

* Update only the specified address owned by the authenticated customer.
* Validate changed fields.
* Allow partial updates without requiring the customer to resubmit every field.
* Prevent invalid values from overwriting valid existing data.
* Ensure customers cannot change address ownership by supplying another customer ID.
* Preserve optional fields when they are omitted from the update request.

### 5. Delete Address

Proposed endpoint: `DELETE /api/customer/addresses/:addressId`

Requirements:

* Delete only an address owned by the authenticated customer.
* Handle nonexistent addresses and unauthorized ownership safely.
* Return a consistent success response.
* Check whether the project has existing order, shipping, or checkout dependencies before deciding between hard deletion and soft deletion.

## Step 3: Required and Optional Validation

Initially, enforce the field rules specified above on the backend.

Validate:

* Required fields are present and not empty.
* String fields have appropriate types and length limits.
* `postalCode` is validated according to the selected country where practical.
* Optional fields are accepted when omitted.
* If an optional field is supplied, validate its type and reject invalid values.
* The address ID is valid according to the database's ID format.
* Invalid requests return clear validation errors.

Do not assume that every country's postal code, state, or phone number follows the same format.

## Step 4: Future Admin Configuration

In the future, the admin panel should be able to configure which address fields are required or optional.

For this phase:

* Do not implement the admin UI.
* Do not build a configuration system unless the existing project already has one suitable for this purpose.
* Keep validation maintainable and structured for future extension.
* Explain how configurable field requirements could be stored and enforced.
* Distinguish configurable business rules from structural database constraints.
* Ensure any future configuration cannot bypass customer ownership checks, data integrity, or security validation.

If implementing this feature now would require a major schema change, explain the change before proceeding.

## Step 5: Database and Security

1. Reuse the existing database and ORM.
2. Follow the project's established migration process.
3. If a new address model or table is required, explain the schema changes and relationships before applying them.
4. Ensure one customer can have multiple addresses.
5. Ensure every address is associated with its owning customer.
6. Add appropriate indexes and foreign-key constraints where suitable.
7. Avoid unnecessary schema changes or duplicate models.
8. Use transactions where needed.
9. Follow existing authorization and error-handling middleware.
10. Do not expose internal database errors, credentials, or sensitive information to clients.

## Step 6: Testing

Test the following:

* Creating an address with all required fields.
* Creating an address with optional fields omitted.
* Rejecting missing required fields.
* Retrieving all addresses for the current customer.
* Retrieving a single address owned by the customer.
* Updating an address partially.
* Rejecting invalid updates.
* Deleting an address.
* Rejecting unauthenticated requests.
* Preventing one customer from reading, updating, or deleting another customer's address.
* Handling customers who have no addresses.
* Ensuring existing account, password, authentication, and other APIs continue working.

Use the testing framework already present in the project.
