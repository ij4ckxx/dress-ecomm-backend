## 2. API Endpoints Specification

### 2.1 Get Account Details

Retrieves the currently authenticated customer's profile.

- **Method:** `GET`
- **Path:** `/api/customer/account` *(or `/api/v1/customer/account`)*
- **Auth Required:** Yes (`Bearer <token>`)

#### Request Headers:
```http
Authorization: Bearer <jwt_access_token>
```

#### Success Response (`200 OK`):
```json
{
  "success": true,
  "message": "Account details fetched successfully",
  "data": {
    "account": {
      "id": "7ca5ddb0-c6d7-43b5-bc13-3595a94ce1d4",
      "firstName": "John",
      "lastName": "Doe",
      "name": "John Doe",
      "email": "john.doe@example.com",
      "phoneNumber": "+1 555-123-4567",
      "phone": "+1 555-123-4567",
      "role": "CUSTOMER",
      "avatarUrl": null,
      "createdAt": "2026-10-11T12:00:00.000Z",
      "updatedAt": "2026-10-11T12:30:00.000Z"
    }
  }
}
```

#### Error Response (`401 Unauthorized`):
```json
{
  "success": false,
  "message": "Authentication required. Please log in to proceed.",
  "error": {
    "code": "UNAUTHORIZED"
  }
}
```

### 2.2 Update Account Details

Updates the authenticated customer's profile information. The customer's identity is strictly obtained from the token, preventing client spoofing.

- **Method:** `PATCH` or `PUT`
- **Path:** `/api/customer/account` *(or `/api/v1/customer/account`)*
- **Auth Required:** Yes (`Bearer <token>`)

#### Request Headers:
```http
Content-Type: application/json
Authorization: Bearer <jwt_access_token>
```

#### Request Body:
```json
{
  "firstName": "John",
  "lastName": "Doe",
  "email": "john.doe@example.com",
  "phoneNumber": "+1 555-123-4567"
}
```
*(Note: Both `phoneNumber` and `phone` keys are accepted for client convenience).*

#### Success Response (`200 OK`):
```json
{
  "success": true,
  "message": "Account details updated successfully",
  "data": {
    "account": {
      "id": "7ca5ddb0-c6d7-43b5-bc13-3595a94ce1d4",
      "firstName": "John",
      "lastName": "Doe",
      "name": "John Doe",
      "email": "john.doe@example.com",
      "phoneNumber": "+1 555-123-4567",
      "phone": "+1 555-123-4567",
      "role": "CUSTOMER",
      "avatarUrl": null,
      "createdAt": "2026-10-11T12:00:00.000Z",
      "updatedAt": "2026-10-11T12:35:00.000Z"
    }
  }
}
```

#### Error Response - Missing Required Field (`400 Bad Request`):
```json
{
  "success": false,
  "message": "Last name is required",
  "error": {
    "code": "VALIDATION_ERROR",
    "details": [
      {
        "field": "lastName",
        "message": "Last name is required"
      }
    ]
  }
}
```

#### Error Response - Duplicate Email (`409 Conflict`):
```json
{
  "success": false,
  "message": "An account with this email address already exists",
  "error": {
    "code": "EMAIL_ALREADY_EXISTS"
  }
}
```

### 2.3 Change Password

Updates the customer's password after verifying their current password. Inactivates all existing refresh token sessions for security.

- **Method:** `PATCH` or `PUT`
- **Path:** `/api/customer/account/password` *(or `/api/v1/customer/account/password`)*
- **Auth Required:** Yes (`Bearer <token>`)

#### Request Headers:
```http
Content-Type: application/json
Authorization: Bearer <jwt_access_token>
```

#### Request Body:
```json
{
  "currentPassword": "CurrentPassword123",
  "newPassword": "NewStrongPassword456"
}
```

#### Success Response (`200 OK`):
```json
{
  "success": true,
  "message": "Password changed successfully. Please log in again with your new password."
}
```

#### Error Response - Incorrect Current Password (`400 Bad Request`):
```json
{
  "success": false,
  "message": "Current password is incorrect",
  "error": {
    "code": "INVALID_CURRENT_PASSWORD"
  }
}
```

#### Error Response - Weak Password (`400 Bad Request`):
```json
{
  "success": false,
  "message": "Password must be at least 8 characters long",
  "error": {
    "code": "VALIDATION_ERROR",
    "details": [
      {
        "field": "newPassword",
        "message": "New password must be at least 8 characters long"
      }
    ]
  }
}
```

#### Error Response - Identical Password (`400 Bad Request`):
```json
{
  "success": false,
  "message": "New password must be different from current password",
  "error": {
    "code": "VALIDATION_ERROR",
    "details": [
      {
        "field": "newPassword",
        "message": "New password must be different from current password"
      }
    ]
  }
}
```

## 3. Database & Schema Strategy

1. **Non-Breaking Compatibility:**
   - The Prisma [`User`](file:///d:/Projects/dress-ecomm-backend/prisma/schema/auth.prisma#L8-L38) table stores `name: String` and `phone: String?`.
   - `firstName` and `lastName` are dynamically combined into `name` (`${firstName} ${lastName}`) on update, and safely parsed via [`splitName`](file:///d:/Projects/dress-ecomm-backend/src/services/client/customer.service.js#L11) on read.
   - This ensures **zero database schema migration risks**, and preserves 100% compatibility with the Admin Panel, Auth Service, and Order modules.
2. **Session Revocation on Password Change:**
   - When a password is changed, all stored `RefreshToken` rows belonging to that `userId` are purged (`prisma.refreshToken.deleteMany({ where: { userId } })`), ensuring stolen or stale sessions are terminated.

## 4. Admin Configurability Analysis (Step 4 Blueprint)

In the future, the Admin Panel may allow configuring which fields are required or optional (e.g., making `phoneNumber` mandatory for SMS delivery notifications or `lastName` optional for single-name cultures).

### Architectural Design:
1. **Separation of Concerns:**
   - In [`src/validators/customer.validator.js`](file:///d:/Projects/dress-ecomm-backend/src/validators/customer.validator.js), rules are driven by `ACCOUNT_FIELD_CONFIG`.
   - When the admin configuration module is built, this configuration can be fetched from the database [`StoreConfig`](file:///d:/Projects/dress-ecomm-backend/prisma/schema/settings.prisma) or NodeCache.
2. **Structural vs. Configurable Constraints:**
   - **Non-Configurable (Security-Critical):** Email uniqueness, email format, password complexity, and JWT ownership checks must **never** be made optional.
   - **Configurable (Presentation/Contact):** `phoneNumber` (optional vs. required), `lastName` (optional vs. required).
