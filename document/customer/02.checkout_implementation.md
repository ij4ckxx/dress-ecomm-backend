# Implement Customer Checkout — BigCommerce-Inspired Flow

## 1. Objective

Implement a complete checkout flow for my existing dress e-commerce application, inspired by BigCommerce checkout.

Before making any changes, inspect the existing frontend, backend, cart functionality, customer authentication, address APIs, database schema, product pricing, inventory management, and email configuration.

Follow the existing project structure and conventions. Use optimized, reusable, maintainable function-based code. Do not use classes.

**Do not break existing functionality.** If any existing functionality, API, or database schema must change, explain the proposed changes and their impact before proceeding.

## 2. Checkout Flow

Implement the checkout flow in the following order:

1. Customer authentication.
2. Shipping address.
3. Billing address.
4. Payment method selection.
5. Place order.
6. Order processing and email notifications.
7. Redirect to an order confirmation page, which will be discussed and implemented separately after checkout is completed.

### Step 1: Customer Authentication

* If the customer is not logged in, require login before proceeding with checkout.
* After successful login, return the customer to checkout without losing their cart.
* Use the existing authentication implementation.
* Retrieve the customer's email and saved addresses where available.
* Do not create duplicate authentication functionality.

### Step 2: Shipping Address

* Allow the customer to select an existing saved address.
* Allow the customer to add a new address or edit an existing address where appropriate.
* Validate all required address fields on the backend.
* Use the existing customer address functionality wherever possible.
* Associate the selected shipping address with the order.

### Step 3: Billing Address

* Allow the customer to use the shipping address as the billing address.
* Allow the customer to select or enter a different billing address.
* Validate billing details according to the applicable requirements.
* Store the billing address associated with the order.
* Preserve the order's address information even if the customer later edits their saved addresses.

### Step 4: Order Summary

Display a complete order summary similar to BigCommerce checkout.

Include:

* Product image and name.
* Selected product variants, such as size and color, where applicable.
* Quantity and unit price.
* Item subtotal.
* Discounts.
* Applied coupon or gift certificate, if supported by the existing system.
* Shipping charges.
* Taxes.
* Final payable total.
* An option to return to the cart.

All prices, discounts, shipping charges, taxes, and totals must be recalculated and verified on the backend. Never trust totals submitted by the frontend.

Clearly display the currency used for the order.

### Step 5: Payment Methods

Initially, support the following payment methods.

#### A. Razorpay

* Integrate Razorpay using its supported payment flow.
* Support eligible credit cards and debit cards through Razorpay's available payment methods.
* Allow other payment methods only when enabled and supported by the Razorpay integration.
* Create payment orders on the backend.
* Verify Razorpay payment signatures on the backend.
* Verify payment status before marking an order as paid.
* Never store raw card numbers, CVV values, or other sensitive card details in our database.
* Keep Razorpay keys and secrets in environment variables.
* Handle successful, failed, cancelled, and pending payments safely.
* Prevent duplicate order creation and duplicate payment processing.

Do not implement a custom card-processing system or collect raw card details directly.

#### B. Cash on Delivery (COD)

* Provide Cash on Delivery as a separate payment option.
* Require a valid customer email address and phone number for COD orders.
* If the phone number is missing, ask the customer to provide it before placing the order.
* Validate contact information on the backend.
* Store the selected payment method with the order.
* COD orders must not be marked as paid when they are first placed.
* Check whether COD availability should depend on shipping address, order amount, or other business rules. Do not invent restrictions without documenting them.

### Step 6: Place Order

When the customer clicks Place Order:

1. Validate authentication, shipping address, billing address, cart items, inventory, and payment method.
2. Recalculate all order amounts on the backend.
3. Verify that products and selected variants are valid and available.
4. Create an order with an initial status appropriate to its payment method and workflow.
5. Save the ordered product details, quantities, prices, discounts, tax, shipping, currency, and final total.
6. Save the shipping and billing address snapshots.
7. Associate the order with the authenticated customer.
8. Process or verify payment when Razorpay is selected.
9. Prevent duplicate orders caused by repeated clicks, retries, or payment callbacks.
10. Send the appropriate order notification email after the relevant order event is confirmed.

Handle payment failures and unexpected errors without incorrectly marking an order as paid or confirmed.

Use database transactions and idempotency where appropriate. Design the order and payment workflow to handle external payment calls safely.

## 3. Order Data and Pricing

The order must preserve the details of the purchased items at the time of purchase.

Store or reference the necessary information for:

* Order number.
* Customer.
* Product name and identifier.
* Product variant, where applicable.
* Product image or suitable order-history image reference.
* Quantity.
* Unit price.
* Discount.
* Tax.
* Shipping charge.
* Line-item total.
* Order subtotal.
* Final order total.
* Currency.
* Shipping address.
* Billing address.
* Payment method.
* Payment status.
* Order status.
* Creation and update timestamps.

Historical orders must not change their purchased prices when product prices are updated later.

Inspect the existing database models first and reuse or extend them rather than introducing duplicate order or payment models.

## 4. Admin Notification and COD Approval Workflow

For COD orders, the initial requirement is to notify the admin by email when a customer places an order.

The admin should be able to review the order and approve or reject it.

Proposed workflow:

1. Customer places a COD order.
2. The order is created with a suitable initial status.
3. Admin receives an email containing the order reference and a link to review it in the admin panel.
4. Admin reviews the customer details, contact information, shipping address, ordered products, and total.
5. Admin approves or rejects the order through an authenticated admin interface or existing order-management API.
6. The order status is updated accordingly.
7. The customer receives an appropriate email notification.

Email links must not allow anyone to approve or reject orders without proper authentication and authorization.

Do not expose sensitive customer or payment information unnecessarily in email content.

Inspect the existing admin panel and order-management APIs before implementing this workflow. If the required admin functionality does not exist, identify the missing components and explain the implementation scope.

For Razorpay orders, design the workflow around verified payment results and the existing business rules. Do not automatically apply the COD approval process to prepaid orders unless required by the existing order workflow.

## 5. Order Statuses

I want an order lifecycle similar to BigCommerce, with understandable statuses such as:

* Pending
* Awaiting Payment
* Awaiting Fulfillment
* Partially Shipped
* Shipped
* Completed
* Cancelled
* Declined
* Refunded

Inspect the existing project and its current order statuses before implementing anything.

These are reference statuses, not a requirement to introduce every status immediately. Recommend the statuses and transitions appropriate for our application.

Requirements:

* Keep payment status separate from fulfillment/order status where appropriate.
* COD orders awaiting admin review must have an appropriate pending or review status.
* Prepaid orders must not enter fulfillment before payment is verified, unless the established business rules explicitly allow it.
* Admin approval must trigger only valid status transitions.
* Record status changes and timestamps where appropriate.
* Prevent invalid transitions and unauthorized status updates.

Document the final status lifecycle and explain how the customer and admin will see each status.

## 6. Email Notifications

Use the existing email service if available.

Initially, support:

* Admin notification for a newly placed COD order.
* Customer notification when an order is accepted or confirmed according to the applicable workflow.
* Customer notification when a COD order is approved or rejected.
* Appropriate payment-success or payment-failure notifications where supported.

Emails should contain relevant order information, including the order reference, purchased items, quantities, prices, and total.

Do not send a successful-payment or confirmed-order email before the corresponding event is verified.

Use the existing email configuration. If no email service exists, explain the recommended integration and required environment variables before adding a new dependency.

## 7. Security and Reliability

* Authenticate customers before placing orders.
* Authorize admin-only order approval and status changes.
* Verify payment signatures and payment status on the backend.
* Validate all request data on the backend.
* Calculate prices and totals on the backend.
* Prevent price manipulation and unauthorized order access.
* Prevent duplicate orders and duplicate payment processing.
* Handle stock availability and concurrent checkout attempts safely.
* Do not expose secrets, raw payment credentials, or sensitive card data.
* Follow the existing API response and error-handling conventions.

## 8. Implementation Approach

Before coding:

1. Inspect the current cart, customer authentication, address APIs, product and variant models, inventory, admin functionality, order models, and email service.
2. Identify what already exists and what must be added.
3. Present the proposed API endpoints, database changes, payment workflow, and order-status lifecycle.
4. Identify any breaking changes or modifications to existing functionality.

Then implement checkout incrementally, reusing existing functionality wherever possible.

If a major database migration or existing API change is necessary, explain the reason and impact before applying it.
