**Document Reference:** `document/customer/04.corrections.md`  
**Date:** October 2026  
**Audience:** Frontend Developers & Integration Team  
**Project:** Maison De Élégance — Backend Standalone Service (`dress-ecomm-backend`)  
**Status:** Implemented, Tested, & Verified (19/19 Automated Tests Passing)

---

## 1. Executive Summary

In response to the comprehensive audit and requirements outlined in `03.clarification_all_over.md`, the following changes have been implemented:

1. **Security Vulnerability Remediated:** Fixed a critical privilege-escalation vulnerability in public customer registration (`POST /api/v1/auth/register`). Public registration now strictly forces `role = 'CUSTOMER'` and ignores any role provided in the request payload.
2. **Session / Refresh Token API Exposed:** Exposed `POST /api/v1/auth/refresh` using the existing cryptographically secure token rotation mechanism and HTTP-only cookie support.
3. **Public Store Settings API Added:** Added `GET /api/v1/settings` so the storefront can fetch theme configurations, currency symbols, feature flags, tax rates, and free-shipping thresholds without administrative authorization.
4. **Public Curated Collections / Lookbooks APIs Added:** Added `GET /api/v1/collections` and `GET /api/v1/collections/:slug` to serve the lookbook capsule pages without requiring admin privileges.
5. **Zero Breaking Changes:** All existing database models, Prisma schemas, admin modules, customer accounts, address management, category trees, product discoveries, and cart operations remain 100% intact.
6. **Strict Scope Compliance:** Wishlist, Customer Orders, Checkout, and Payment Processing remain untouched and are deferred to the dedicated checkout implementation phase.

## 2. Security & Authentication Updates

### 2.1 Customer Registration (`POST /api/v1/auth/register`)
* **Endpoint:** `POST /api/v1/auth/register` (also `/api/auth/register`)
* **Access:** Public
* **Change Summary:** Removed the `role` field from input validation. The backend strictly guarantees that users created through this public route receive `role: "CUSTOMER"`. (Admin and Staff user creation remains isolated under `/api/v1/admin/users` with RBAC authorization).
* **Request Body:**
  ```json
  {
    "name": "Jane Doe",
    "email": "jane.doe@example.com",
    "password": "Password123!",
    "phone": "+91 98765 43210"
  }
  ```
* **Success Response (`201 Created`):**
  ```json
  {
    "success": true,
    "statusCode": 201,
    "message": "Registration successful",
    "data": {
      "user": {
        "id": "c1f77d85-1234-4567-8901-abcdef123456",
        "name": "Jane Doe",
        "email": "jane.doe@example.com",
        "role": "CUSTOMER",
        "phone": "+91 98765 43210",
        "createdAt": "2026-10-12T17:15:00.000Z"
      }
    }
  }
  ```

### 2.2 Token Refresh (`POST /api/v1/auth/refresh`)
* **Endpoint:** `POST /api/v1/auth/refresh` (also `/api/auth/refresh`)
* **Access:** Public (Requires valid active refresh token)
* **Description:** When the customer's 15-minute JWT access token expires, call this endpoint to obtain a new access token without requiring re-login. The backend implements **token rotation** (the old refresh token is revoked and replaced with a newly issued refresh token).
* **Token Resolution:**
  - **Option A (Recommended for Web):** Automatically reads `refreshToken` from the secure HttpOnly cookie `refreshToken` sent with `credentials: 'include'`.
  - **Option B (Mobile / API clients):** Provide `refreshToken` directly in the JSON body:
    ```json
    {
      "refreshToken": "7c98b64e..."
    }
    ```
* **Success Response (`200 OK`):**
  ```json
  {
    "success": true,
    "statusCode": 200,
    "message": "Token refreshed successfully",
    "data": {
      "user": {
        "id": "c1f77d85-1234-4567-8901-abcdef123456",
        "name": "Jane Doe",
        "email": "jane.doe@example.com",
        "role": "CUSTOMER"
      },
      "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
    }
  }
  ```
* **Cookie Update:** A new `refreshToken` cookie is automatically set in the `Set-Cookie` response header with `HttpOnly`, `SameSite`, and `Secure` attributes.
* **Error Response (`401 Unauthorized`):** If the refresh token is missing, expired, revoked, or previously used.
  ```json
  {
    "success": false,
    "statusCode": 401,
    "message": "Refresh token is invalid or expired",
    "error": {
      "code": "INVALID_REFRESH_TOKEN"
    }
  }
  ```

## 5. Cart Pricing Review & Next Steps for Checkout

### 5.1 Current Cart Pricing Model
The current `GET /api/v1/cart` endpoint calculates:
* `subtotal`: $\sum (\text{item unit price} \times \text{quantity})$
* `modifiersTotal`: $\sum (\text{modifier delta} \times \text{quantity})$
* `total`: $\text{subtotal} + \text{modifiersTotal}$
* `discounts`: `[]` (not yet computed in cart)
* `shipping`: `null` (not yet computed in cart)
* `tax`: `null` (not yet computed in cart)

### 5.2 Business Considerations for Frontend Team Ahead of Checkout:
1. **Shipping Calculation:**
   - Free shipping threshold is set at **₹2,999.00** (`freeShippingThreshold`).
   - If cart total is below ₹2,999, flat delivery is **₹150.00** (`flatShippingRate`).
   - *Decision:* Should the cart page show an estimated shipping rate before address entry, or should final shipping be calculated in the checkout step?
2. **Tax (GST):**
   - In luxury eveningwear in India, 12% GST applies.
   - *Decision:* Is product catalog pricing already tax-inclusive (MRP) or should 12% GST be added at checkout?
3. **Coupons:**
   - Coupons (`LUXE10`, `WELCOME1000`) are stored in `prisma.coupon`.
   - In the upcoming checkout phase, we will provide `POST /api/v1/coupons/validate` and `POST /api/v1/checkout/summary` to preview discounts before order submission.
