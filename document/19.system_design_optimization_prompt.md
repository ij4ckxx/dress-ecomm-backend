# Full Ecommerce Backend Architecture, Performance, and Reliability Audit

Act as a senior Node.js backend engineer, database performance engineer, and system design architect.

My ecommerce project already has most of its core functionality implemented. I want to make the existing backend production-ready, reliable under high concurrency, secure, maintainable, and scalable.

My long-term target is to support approximately 10,000 concurrent customers without unacceptable latency, request failures, data corruption, or order-processing problems.

Important: 10,000 concurrent customers is a design target, not a claim that the current infrastructure can already support this load. Determine what the actual system can handle through profiling and load testing.

## Core Rules

- Inspect the existing codebase before proposing changes.
- Preserve the current architecture and functionality wherever possible.
- Do not rewrite the application from scratch.
- Do not introduce microservices unless there is a demonstrated need.
- Do not install BullMQ, Redis, clustering, or a load balancer merely because they are common technologies.
- Reuse existing implementations when they are correct.
- Avoid unnecessary dependencies and infrastructure costs.
- Prefer simple, measurable improvements before complex architectural changes.
- Do not modify files until the initial audit and implementation plan are presented and approved.

## 1. Map the Existing Architecture

Inspect the complete backend, including:

- Application entry points and server initialization.
- Routes, middleware, controllers, services, and database access.
- Authentication, authorization, and admin permission checks.
- Prisma schema, database queries, transactions, and connection pooling.
- Customer-facing and admin APIs.
- Cart, checkout, orders, inventory, and payment workflows.
- Email notifications and external API integrations.
- File and image storage.
- Scheduled tasks, workers, and existing queues.
- Error handling, validation, logging, configuration, and deployment files.
- Existing rate limiting, caching, and security middleware.
- Docker configuration and CI/CD configuration, if present.

Identify architectural inconsistencies, duplicated logic, hidden bottlenecks, and single points of failure.

Trace important workflows across layers instead of judging files independently.

## 2. Establish Performance Baselines

Identify the most important API endpoints and their expected workloads.

Prioritize:

- Product listing, search, filtering, and product details.
- Customer authentication and account endpoints.
- Cart and checkout.
- Order creation and order history.
- Payment processing and webhooks.
- Admin product and inventory management.
- Admin order listing and dashboard statistics.

Recommend how to measure:

- Requests per second.
- Concurrent requests and active connections.
- Response latency, including p50, p95, and p99.
- Error rates and timeouts.
- CPU and memory usage.
- Database query latency and connection-pool saturation.
- Redis and queue performance, if applicable.

Identify the slowest or most resource-intensive operations first. Do not optimize based solely on assumptions.

## 3. Database and Prisma Optimization

Review database queries, indexes, connection pooling, transactions, and pagination.

Specifically investigate:

- N+1 queries and repeated database calls.
- Unnecessary relation loading and oversized responses.
- Full-table scans and inefficient filtering.
- Offset pagination on large datasets where cursor pagination may be more appropriate.
- Expensive aggregate queries and admin dashboard calculations.
- Long-running transactions and excessive database connections.
- Concurrent inventory updates and duplicate order creation.
- Database constraints and data integrity.
- Transaction boundaries for checkout and order status changes.

Recommend appropriate optimizations with evidence from the actual code.

Do not weaken consistency requirements merely to increase throughput.

## 4. Concurrency and Order Reliability

Treat checkout, inventory, orders, and payments as critical workflows.

Verify that:

- Concurrent purchases cannot oversell inventory.
- Duplicate requests do not create duplicate orders or charges.
- Payment webhooks are idempotent.
- Invalid order status transitions are rejected.
- Order creation and associated database updates are transactionally consistent.
- External payment or email calls are not unnecessarily performed inside long database transactions.
- Failed operations have safe recovery and compensation strategies.
- Stock reservation, release, and cancellation behavior is correct.
- Retrying a request does not corrupt business state.

Explain which guarantees are currently implemented and which are missing.

Do not introduce distributed locks or complex distributed transactions unless simpler database-level solutions are insufficient.

## 5. BullMQ, Redis, and Background Processing

Determine whether background processing is necessary and identify suitable workloads.

Evaluate BullMQ for:

- Order confirmation and shipping emails.
- Admin notifications.
- PDF or invoice generation.
- Retryable external API operations.
- Scheduled tasks and cleanup.
- Other CPU-intensive or long-running operations found in the project.

If appropriate, design a worker architecture with:

- Separate worker processes.
- Bounded concurrency.
- Retry policies and exponential backoff.
- Job idempotency.
- Failed-job monitoring and recovery.
- Queue retention and cleanup.
- Graceful worker shutdown.
- Queue backlog monitoring.

Evaluate Redis for caching, shared rate limiting, and BullMQ storage.

If reliable event delivery between PostgreSQL and Redis is required, consider a transactional outbox rather than assuming a database transaction and queue insertion are atomic.

Clearly identify which work must remain synchronous and which can safely be asynchronous.

## 6. Rate Limiting and API Security

Audit the existing rate limiter rather than replacing it automatically.

Check:

- Login, registration, password reset, and other sensitive endpoints.
- Public API abuse and expensive search endpoints.
- Checkout and payment abuse.
- Distributed rate limiting across multiple API instances.
- Client IP identification and trusted proxy configuration.
- Request body size limits and validation.
- Authentication and role-based authorization.
- CORS, security headers, and secret management.
- Protection against unauthorized admin actions and mass assignment.
- Secure handling of cookies, JWTs, and refresh tokens.
- Sensitive information in logs and error responses.

Preserve legitimate customer behavior while preventing abuse.

## 7. Caching Strategy

Determine which operations benefit from caching.

Evaluate:

- Product and category data.
- Navigation metadata.
- Public read-heavy endpoints.
- Expensive aggregate results.
- Other repeated queries identified during profiling.

For each proposed cache, document:

- Cache key design.
- TTL.
- Invalidation strategy.
- Stale-data tolerance.
- Memory usage.
- Behavior when Redis is unavailable.

Avoid unsafe caching of user-specific data, payment status, or inventory information.

Do not introduce caching where query optimization alone is sufficient.

## 8. Scaling Toward 10,000 Concurrent Customers

Assess the actual requirements before selecting infrastructure.

Evaluate:

- Whether the API is stateless.
- Node.js event-loop utilization and CPU-bound work.
- Horizontal scaling versus a single instance.
- Node.js clustering where appropriate.
- Load balancers and health checks.
- Database connection budgets across all instances.
- Redis availability and shared state.
- Queue worker scaling.
- CDN and image delivery.
- Autoscaling, deployment strategy, and graceful shutdown.
- Database read replicas or partitioning only if justified by measured bottlenecks.

Estimate resource requirements using explicit assumptions and load-test results.

Distinguish between 10,000 connected or active users, 10,000 concurrent in-flight requests, and 10,000 users browsing over a period of time. These are different workloads.

Do not promise that the target is achievable until the architecture has been tested under representative traffic.

## 9. Failure Handling and Production Stability

Inspect how the application behaves when:

- PostgreSQL becomes slow or unavailable.
- Redis becomes unavailable.
- An email provider times out.
- A queue worker crashes.
- A payment provider sends duplicate or delayed webhooks.
- The API receives traffic spikes.
- A database connection pool is exhausted.
- A deployment terminates an instance during active requests.

Recommend timeouts, bounded retries, graceful shutdown, health checks, readiness checks, and recovery mechanisms where appropriate.

Avoid retry storms, unlimited queues, and unbounded concurrency.

Identify which components are critical dependencies and whether they need redundancy or a documented recovery plan.

## 10. Observability and Testing

Recommend practical monitoring and testing for this project.

Include:

- Structured logs with request IDs.
- Error tracking.
- API latency and error metrics.
- Database and connection-pool metrics.
- Queue depth and job failure metrics, if queues exist.
- Health and readiness endpoints.
- Unit, integration, and end-to-end tests for critical flows.
- Load testing with realistic customer and admin traffic.
- Stress testing and soak testing.
- Failure-injection tests for critical dependencies.

Recommend measurable acceptance criteria for latency, throughput, error rates, and recovery behavior. Establish targets based on the application's requirements rather than inventing guarantees.

## 11. Required Audit Report

Before changing any files, produce the following:

1. Current architecture and request-flow diagram.
2. Existing functionality and infrastructure inventory.
3. Confirmed bottlenecks and reliability risks, with file paths and code references.
4. Critical correctness and security issues.
5. Database optimization findings.
6. BullMQ, Redis, rate limiter, and load-balancer recommendations.
7. Scaling strategy for the 10,000-concurrent-customer target.
8. Failure-handling and observability gaps.
9. A prioritized implementation plan divided into:
   - Phase 1: Correctness and critical bugs.
   - Phase 2: Low-risk performance improvements.
   - Phase 3: Background processing and caching where justified.
   - Phase 4: Horizontal scaling and infrastructure.
   - Phase 5: Load testing and production validation.
10. For every proposed change, describe its expected benefit, complexity, risk, cost, dependencies, and validation method.

Classify every finding as confirmed, suspected, or requiring measurement.

## 12. Implementation Rules After Approval

Once I approve a specific phase:

- Implement only the approved scope.
- Preserve existing APIs and response formats unless a change is necessary and approved.
- Follow the current project conventions and folder structure.
- Do not replace working code unnecessarily.
- Add or update tests for affected functionality.
- Avoid destructive database operations.
- Update environment examples and deployment documentation when needed, without exposing secrets.
- Run available linting, type checks, tests, and builds.
- Report changed files, reasoning, test results, remaining risks, and rollback considerations.

Start with a complete read-only audit. Do not implement changes until I review and approve the report.
