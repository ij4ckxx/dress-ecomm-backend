# Clean Code Standards

## Instructions & Rules

### 1. Functional Programming
- Always prefer functions and arrow functions.
- Do not use classes or class-based implementations.
- Avoid unnecessary object-oriented patterns.
- Keep functions focused on a single responsibility.
- Prefer pure functions wherever practical.
- Avoid unnecessary side effects.
- Use early returns to reduce nested conditions.

### 2. Function Documentation
- Every function must have a meaningful documentation comment immediately above its definition.
- Explain what the function does and its primary responsibility.
- Mention important parameters or return values when they are not obvious.
- Keep descriptions short, clear, and meaningful.
- Do not write meaningless comments such as "This is a function."

Example:

```javascript
/**
 * Calculates the final price after applying the discount percentage.
 */
const calculateFinalPrice = (price, discount) => {
  if (!discount) return price;

  return price - (price * discount) / 100;
};
```

### 3. Naming Conventions
- Use descriptive names for variables, functions, parameters, and constants.
- Function names should clearly describe their actions.
- Use camelCase for variables and functions.
- Use PascalCase for React components and types where appropriate.
- Avoid unclear abbreviations and single-letter names unless commonly accepted.

### 4. Code Readability
- Keep functions small and easy to understand.
- Avoid deeply nested conditions.
- Avoid unnecessary ternary operators and complex expressions.
- Break complicated logic into smaller reusable functions.
- Avoid unnecessary comments when code is self-explanatory.
- Maintain consistent formatting and indentation.

### 5. Error Handling
- Handle errors intentionally.
- Do not silently swallow errors.
- Avoid unnecessary try/catch blocks.
- Return meaningful errors where appropriate.
- Follow the existing project's error-handling conventions.

### 6. Dependencies
- Do not install new packages without a valid reason.
- Prefer existing libraries and utilities.
- Avoid introducing dependencies for functionality that can be implemented simply with existing tools.

### 7. General Principles
- Follow KISS (Keep It Simple).
- Follow DRY (Don't Repeat Yourself).
- Follow SOLID principles where applicable without forcing object-oriented patterns.
- Avoid premature optimization.
- Do not over-engineer simple requirements.
- Prefer maintainable solutions over clever implementations.

## Before Completing Any Task

1. Review the code for readability.
2. Check for duplicate logic.
3. Ensure every function has proper documentation.
4. Verify that no unnecessary complexity was introduced.
5. Ensure existing functionality remains unchanged.

# Project Architecture Guidelines

## Instructions & Rules

### 1. Understand Before Implementing
- Always inspect the existing folder structure before making changes.
- Understand how the existing application is organized.
- Identify the relevant modules, components, services, utilities, and configurations.
- Check how similar functionality is already implemented.
- Never assume the project follows a standard architecture.

### 2. Follow Existing Folder Structure
- Always place new files in their appropriate existing directories.
- Do not introduce unnecessary folders.
- Do not create alternative folder structures for existing functionality.
- Follow existing file naming conventions.
- Keep related functionality together.
- Do not move or rename existing files unless explicitly required or technically necessary.

### 3. Separation of Concerns
- Keep UI components separate from business logic.
- Keep API communication in the appropriate service or API layer.
- Keep database operations in the existing database layer.
- Keep shared utilities in their designated location.
- Keep authentication and authorization logic in the appropriate server-side layer.
- Avoid mixing unrelated responsibilities in a single file.

### 4. Maintain Existing Architecture
- Extend existing modules instead of rebuilding them.
- Follow established import and export patterns.
- Respect existing server/client boundaries.
- Follow the current routing conventions.
- Reuse existing providers, layouts, middleware, and configuration.
- Do not introduce architectural changes for small feature requests.

### 5. File Creation Rules
Before creating a new file:
1. Search for an existing implementation.
2. Identify the correct directory.
3. Check whether the functionality belongs in an existing file.
4. Create a new file only when it improves organization or reuse.
5. Follow the existing naming conventions.

### 6. Dependency Management
- Understand existing dependencies before adding new ones.
- Avoid duplicate libraries that solve the same problem.
- Do not upgrade package versions unnecessarily.
- Check compatibility before changing dependencies.

### 7. Database and Configuration
- Follow the existing database architecture.
- Never duplicate environment variable definitions.
- Keep secrets out of source code.
- Avoid modifying existing configurations without understanding their impact.
- Preserve existing environment variable naming conventions.

## Before Completing Any Task

1. Verify that files are located in the correct directories.
2. Ensure no unnecessary folders or files were created.
3. Check that imports and exports follow existing conventions.
4. Confirm that the architecture remains consistent.
5. Report all newly created, modified, and deleted files.

# Reusable Components and Utilities

## Instructions & Rules

### 1. Search Before Creating
- Always search the existing codebase before creating a new function, component, hook, utility, or service.
- Check whether an equivalent implementation already exists.
- Reuse or extend existing implementations whenever possible.
- Never create duplicate functions with slightly different names to solve the same problem.

### 2. Reusable Functions
- Extract common logic into reusable functions.
- Keep each function focused on one responsibility.
- Accept parameters instead of hardcoding values.
- Avoid unnecessary dependencies between functions.
- Use shared utilities for commonly repeated operations.
- Document every function with a meaningful comment.

### 3. Reusable React Components
- Build components that can be reused across multiple pages.
- Use props to customize component behavior and appearance.
- Avoid hardcoding page-specific content inside shared components.
- Keep components focused on a single responsibility.
- Follow existing component composition patterns.
- Reuse existing UI primitives before creating new ones.

### 4. Custom Hooks
- Reuse existing hooks wherever possible.
- Create custom hooks when stateful or reusable React logic needs to be shared.
- Follow React hook naming conventions.
- Never call hooks conditionally.
- Avoid creating hooks for simple logic that can remain inside a component.

### 5. Shared Constants
- Store commonly used static values in appropriate shared constant files.
- Avoid repeating hardcoded strings and values.
- Reuse existing enums, constants, and configuration objects.
- Keep configuration values centralized when appropriate.

### 6. Validation and API Logic
- Reuse existing validation schemas.
- Avoid duplicating request and response handling logic.
- Reuse existing API clients and service functions.
- Keep shared validation rules consistent across frontend and backend where appropriate.

### 7. Avoid Over-Abstraction
- Do not create reusable abstractions unnecessarily.
- Not every small function needs a separate file.
- Do not create components solely to reduce a few lines of JSX.
- Avoid generic solutions when a simple specific implementation is better.
- Create abstractions when they provide clear reuse, consistency, or maintainability benefits.

## Before Completing Any Task

1. Search for duplicated logic.
2. Identify opportunities to reuse existing functions.
3. Verify shared components are configurable.
4. Ensure abstractions are not unnecessarily complicated.
5. Confirm there is a single source of truth for shared functionality.

# Next.js Frontend Development

## Instructions & Rules

### 1. Server Components First
- Prefer React Server Components by default.
- Use Client Components only when browser-side interactivity is required.
- Add "use client" only when necessary.
- Do not convert an entire page into a Client Component for a small interactive section.
- Keep server-side data fetching on the server whenever possible.
- Follow existing Next.js routing conventions.

### 2. Server-Side Rendering
- Prefer SSR and server-side data fetching where appropriate.
- Avoid unnecessary client-side fetching.
- Use Server Actions when suitable for server-side form submissions and mutations.
- Never expose server-only secrets or sensitive logic to the browser.
- Follow existing caching and revalidation strategies.

### 3. React Development
- Use functional components only.
- Never create class components.
- Use React hooks appropriately.
- Avoid unnecessary useEffect and useState.
- Avoid unnecessary re-renders.
- Keep components small and maintainable.
- Separate complex reusable logic into appropriate hooks or utility functions.

### 4. UI Components
- Inspect existing components before creating new ones.
- Reuse the existing component library.
- Follow existing Tailwind CSS conventions.
- Use semantic HTML elements.
- Build accessible forms, buttons, dialogs, and navigation.
- Avoid introducing another UI library when an equivalent already exists.
- Keep UI components separate from business logic where appropriate.

### 5. Responsive Design
- Ensure pages work on mobile, tablet, and desktop.
- Follow the project's existing responsive breakpoints.
- Avoid fixed widths when responsive layouts are more appropriate.
- Maintain consistent spacing, typography, and alignment.
- Avoid breaking existing layouts.

### 6. Forms and Validation
- Reuse existing form libraries and validation schemas.
- Validate user input appropriately.
- Display clear validation and server error messages.
- Prevent unnecessary duplicate submissions.
- Handle loading, success, and error states.

### 7. Performance
- Use Next.js Image for optimized images where appropriate.
- Use appropriate dynamic imports when they provide a benefit.
- Avoid unnecessary dependencies.
- Optimize rendering and data fetching.
- Avoid excessive client-side JavaScript.
- Use appropriate pagination or incremental loading for large datasets.

### 8. Authentication and Authorization
- Perform sensitive authentication and authorization checks on the server.
- Never rely only on frontend route protection.
- Never expose tokens, secrets, or private user data to client components.
- Follow the existing Auth.js and session-handling implementation.

## Before Completing Any Task

1. Check server/client component boundaries.
2. Verify responsive behavior.
3. Check loading, error, and empty states.
4. Verify form validation and accessibility.
5. Check for unnecessary client-side rendering.
6. Ensure existing pages and functionality remain intact.

# Backend API and Database Development

## Instructions & Rules

### 1. Functional Backend Development
- Use functions and arrow functions.
- Never use classes.
- Keep business logic modular and reusable.
- Keep functions focused on a single responsibility.
- Add meaningful documentation comments above every function.
- Use descriptive function and variable names.
- Prefer early returns and simple control flow.

### 2. API Architecture
- Follow the existing backend folder structure.
- Separate route handlers, business logic, and database operations according to the existing architecture.
- Reuse existing API handlers and service functions.
- Follow established request and response formats.
- Use appropriate HTTP methods and status codes.
- Keep API responses consistent.
- Avoid duplicating business logic across endpoints.

### 3. Request Validation
- Validate all incoming request data.
- Never trust client-provided values.
- Reuse existing validation libraries and schemas.
- Validate IDs, quantities, prices, and other important values.
- Reject invalid or unauthorized requests.
- Handle missing and malformed data appropriately.

### 4. Authentication and Authorization
- Verify authentication on protected endpoints.
- Verify authorization independently of authentication.
- Enforce admin-only operations on the server.
- Never trust user roles or permissions provided by the client.
- Protect sensitive user information.
- Follow the existing Auth.js, JWT, session, or cookie implementation.
- Never expose passwords, tokens, secrets, or private database fields.

### 5. Database Operations
- Follow the existing Prisma schema and database architecture.
- Reuse existing queries and database utilities.
- Avoid unnecessary database calls.
- Prevent N+1 query problems.
- Use appropriate indexes for frequently queried fields.
- Implement pagination for large datasets.
- Select only the fields required for each operation.
- Use transactions when multiple database operations must succeed or fail together.
- Avoid unnecessary schema changes.
- Check relationships and constraints before modifying models.

### 6. E-commerce Business Logic
- Never trust prices, discounts, totals, or stock quantities received from the client.
- Calculate important order values on the server.
- Validate product availability before creating orders.
- Prevent unauthorized order access.
- Ensure users can only access their own private data unless they have appropriate admin permissions.
- Validate order status transitions.
- Prevent duplicate order processing where necessary.
- Maintain inventory consistency.
- Handle payment-related operations securely.

### 7. Error Handling
- Handle expected errors explicitly.
- Use consistent error response structures.
- Do not expose internal stack traces or database errors to clients.
- Log useful information for debugging without exposing sensitive data.
- Avoid silently ignoring failed operations.

### 8. Security
- Protect against SQL injection and unsafe queries.
- Use secure cookie settings where applicable.
- Apply appropriate rate limiting.
- Validate file uploads.
- Protect sensitive environment variables.
- Never hardcode credentials or API secrets.
- Follow existing CORS and security-header configurations.

### 9. Scalability and Performance
- Avoid loading unnecessary records.
- Use efficient database queries.
- Apply pagination and filtering.
- Avoid redundant API requests.
- Reuse database connections and existing infrastructure.
- Avoid premature optimization and unnecessary architectural complexity.

## Before Completing Any Task

1. Verify request validation.
2. Check authentication and authorization.
3. Review database query efficiency.
4. Check transaction and data-integrity requirements.
5. Verify error handling and response consistency.
6. Ensure no sensitive information is exposed.
7. Run relevant tests and build checks.
